## Follow-up repair probe, defined after the no-skill output

The first no-skill episode generated three files and received 34 passes and one failure: its DOT output lacks a diamond shape for choice nodes. To test use of feedback rather than merely re-run from scratch, initialize two new isolated no-skill agents with the **same saved output files** and the original task and input. No verifier or test source is mounted. In the neutral condition say only that the output did not satisfy all verifier checks; in the diagnostic condition additionally communicate the actual failing assertion, "Choice nodes should be visualized as diamonds." Both conditions may edit and execute the saved code, receive the same runner and caps, and are independently checked only after execution. Never feed either verifier output from the repair probe back to the other arm.

This is an adaptive development case, not blind confirmation, and the feedback is generated from the held-back verifier; it represents a deployment scenario only when such feedback is actually available. Because these episodes inherit a single initial artifact and one observed failure, a repair is not evidence for cross-task learning or a general skill method. Primary report is all 35 original verifier checks plus artifact validity, errors introduced, and physical calls; no claim based only on the previous 34/35 fraction. Freeze source hashes and keep the original artifacts untouched.

Both first repair agents reached the request limit and neither changed the original DOT; both remain at 34/35. A second, post-hoc budget diagnostic is defined before launching: run fresh neutral and diagnostic agents again from those same three original files, raising the common request ceiling to 16 and body-byte ceiling to 900,000; leave per-step generation and time ceilings unchanged. This is not a continuation of either previous trajectory, and the budget change was motivated by their observed cap failures. It can show what happened under the larger limit, but cannot isolate causal budget effects on a fixed stochastic trajectory. Preserve and report all four repair runs.

**Invalidating harness defect, discovered from the 16-request diagnostic raw:** the agent attempted to write `/app/solution.py` twice and both writes returned `PermissionDenied`. The host copied the initial file with host ownership and mode 0644; the container runs with all capabilities dropped and could not overwrite it. Consequently the four initial repair outcomes cannot evaluate feedback effectiveness. Fix only the cloned copies to mode 0666, keep originals and raw unchanged, and rerun neutral and diagnostic independently under the 16-request/900,000-byte limits. Check the raw for successful actual writes and both verification layers. This correction is post-hoc, not preregistered confirmation.
