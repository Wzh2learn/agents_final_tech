# Invoice fraud-detection Agent development pilot

Before running new episodes, pin SkillsBench v1.1 public `invoice-fraud-detection` task and input files. It is a distinct task family from dialogue parsing and cache replay, but still the same public benchmark; no claim of independent benchmark or pretrained-data isolation. The offline task compares PDF invoices, spreadsheet vendors and purchase orders, under a fixed priority order of five fraud rules; it is a research benchmark, not a real financial decision service.

Run one no-skill and one all-original-skill episode as isolated OpenCode + local Qwen agents; same task statement, input bytes, tool access, 16 accepted HTTP requests, 900,000 cumulative POST-body bytes, 8,192 output tokens per step, 600-second process and 300-second service timeout. The skill arm has extra information and reads the public PDF, spreadsheet and fuzzy-match skills; it is not an equal-information comparison. Docker has no external network; the verifier and `ground_truth.json` do not enter the agent container. Afterward mount the original verifier in a separate network-isolated container and compute record-level precision/recall and reason agreement from saved output and its reference. Report missing output, malformed JSON, number of physical calls, returned usage, wall time, partial outputs and raw failure, not merely pytest status.

Adapted environment: `python:3.12-slim`, mounted local Python 3.12 packages: `pypdf` 6.4.1, `openpyxl` 3.1.5, and isolated `rapidfuzz` 3.14.3. These differ from the upstream Dockerfile's full set of packages and versions; any result is an adapted execution, not an official leaderboard score. The task files are public benchmark materials; preserve source hashes and do not place verifier-derived facts in prompts. If either arm fails, inspect the failure and reference contract before planning any targeted feedback-repair comparison. One episode per arm is a development diagnostic and cannot establish general effects or cross-family transfer.

## Post-hoc same-start repair comparison

The first no-skill run detected all 50 reference-positive pages but only 18 reasons matched; its saved `analyze_fraud.py` rerun yielded 20 reason matches. Inspection of the public vendor table and code independently shows the `partial_ratio` scorer matches `Vendor 11` to `Vendor 1` at 100, `Vendor 31` to `Vendor 3` at 100, and `Vendor 100` to `Vendor 1` at 100. This is a visible-data, code-grounded diagnostic, not a hidden reference answer.

From identical copies of the original `analyze_fraud.py` and `fraud_report.json`, run a neutral agent told the previous output failed checks and a diagnostic agent additionally told that exact vendor names should be preferred before fuzzy matching, and that the report should be regenerated after edits. Match tools, environment, 16 HTTP cap and 900,000-byte cap; allow writes to copied artifacts (mode 0666), preserve originals and never mount the reference in the agent container. Score both after execution and rerun their saved scripts separately to see whether files and generated reports agree. The prompt is post-hoc and the task already observed; results support only a bounded case observation, not generalization.

After observing the diagnostic run, include a deterministic visible-rule control that inserts an exact-vendor-name check ahead of the existing fuzzy scorer in the original program, then reruns it in an isolated container. This is a post-hoc simple baseline with the same diagnostic content, not an independently frozen comparator or a new method; verify its full output separately rather than assuming it works.
