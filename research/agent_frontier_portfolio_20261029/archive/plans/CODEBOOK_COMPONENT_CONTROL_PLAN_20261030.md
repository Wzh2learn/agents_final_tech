# 制造缺陷任务：元件编号匹配的事后确定性对照

2026-10-30，控制运行前。对已经看过的开发轨迹做代码尸检，不是独立确认。无经验 Agent 生成的 `normalize.py` 在 `score_match` 中对小写文本使用 `[A-Z]+[\d]+`，同时对小写 keyword 再使用同一个大写正则；两个门均无法匹配字母。其后预期执行的组件判断是双向子串包含，可能把短编号和长编号当成相同编号。经验组的另一份代码使用组件集合交集，但两次生成的其他逻辑也不同，不能把整体差异归因于记忆。

固定同一原 Agent 程序与 12,000 条公开输入，在隔离容器逐个执行：

1. `original_replay`：原程序逐字节复跑，核对与 Agent 已保存的报告是否一致。
2. `case_substring`：仅修正文本和 keyword 的大小写匹配，保留原双向子串判断。
3. `case_exact`：在第二组基础上将组件判断改为完整编号相等。

保存各程序、输入与输出 SHA-256、原 verifier、运行日志和墙时。事前规定不调用模型、不更改原报告、不让 Agent 看 verifier；相同代码和数据的变更仅为上述差异。先比较所有输出的相同 record/segment/span 的 code 变化，再观察已有 verifier 的通过项变化。输出差异不证明谁的分类准确：原 verifier 使用词项重叠等代理，且参考不足以证明因果或真实工业质量。若原程序复跑与初始报告不一致，后两组仅以实际复跑为对照，不拿原报告当同程序输出。

首次尝试的三个容器均因输出目录权限而未生成报告（各为写文件时 PermissionError），原始日志保留为 `codebook_component_controls`；不能算实验结果。修正独立临时输出目录为可写后，在新目录重新执行全部三组；没有模型调用。

三组完成后进一步核查变化样本：原正则把 `I2C_SCL` 切成 `I2`，可能把它与 `I2C_SDA` 这样的不同信号通过子串绑定。为区分“等值规则”和“标识符切分”，追加事后第四组 `case_signal_exact`：只在 `case_exact` 上把提取改成允许字母、数字及下划线的完整 token，再按完整 token 等值比较；不改变类别打分和其他代码。在新目录全部四组重放，避免覆盖前次。这个新增假设根据已看过的样本提出，只是开发性诊断。正则匹配可见输入得到的是候选片段，不保证它是真正完整的元件标识。
