# 13F 任务规则与评分反馈冲突：真实 Agent 开发实验卡

2026-10-31；本卡须在本实验首次模型请求前与运行器、任务构建器一起提交。这个实验围绕已有[公开任务源码发现](../../FINANCIAL_FEEDBACK_CONTRACT_FINDING_20261031.md)，但**主动增加明确类别合同，属于受控改造任务**，不宣称原始自然语言任务的金融语义只有一个正确答案，也不宣称运行了官方基准。

## 研究问题

旧任务的检查器与任务中明确写出的分类规则产生冲突时，Agent 将真实工具执行、历史答案和反馈用于新任务，会更倾向延续规则、迁移检查器数值口径，还是无法判断？这是经验与反馈学习的开发探针；只在两个管理人、同一公开 Q3 资产上进行，任务/参考已被研究者看到，模型预训练曝光未知。

## 两个受控任务

共用公开 SkillLearnBench `financial-analysis` 的 Q3 ZIP（输入 hash 与[复算](../../skilllearnbench_13f_class_literal_audit_20261031.json)绑定）。任务明确给出同一个 25 项可执行 `TITLEOFCLASS` 列表，要求在 `PERIODOFREPORT=30-SEP-2025` 且 `FILINGMANAGER_NAME` 大小写无关**完整相等**的申报上，统计 `TITLEOFCLASS.lower()` 精确属于该列表的 `INFOTABLE` 行数。T1 管理人为 Renaissance，T2 为 Bridgewater；输出 `/root/count.json`，仅含整数字段 `count`。这定义的是该实验合同下的计数，不能当成独立金融分类 gold 或基金全部 AUM。

实际数据、完整类别合同、可读脚本工具对所有组相同；原 solution、原测试、目标 expected、Q2 报告数据和代码仓库均不放进 Agent 容器。原测试及定制的合同 checker 仅在 Agent 停止后挂载。预先的 CPU 复算确定了隐藏参考，以数据、任务和代码 hash 冻结；gold 只能用于评价和构造已发生的历史反馈，不提供 T2 目标答案。

## 顺序与组别

1. 独立启动一个真实工具 Agent 执行 T1，保留实际 `count.json`、工具轨迹和合约 checker；随后把它的 count 与发布的 T1 原 verifier 比较。为隔离 q2 谓词，原 verifier 的其他三个答案由 expected 填入，其输出构造在独立容器内，**不是 Agent 解决原四题**。
2. 若 T1 未交付可解析整数，则保持失败证据，只运行不依赖历史的 T2，无需虚构前次结果或反馈。若 T1 有值，则在同一 T2 上依次执行独立重启的条件：
   - `no_history`：只有 T2 当前合同。
   - `history_only`：提供 T1 实际输出和同一规则的历史摘要，不给反馈结论。
   - `history_contract_feedback`：与上面同一实际历史，加合同 checker 的实际结果与 T1 合同计数。
   - `history_upstream_feedback`：与同一实际历史，加原测试实际结果及 T1 发布参考计数。
   - `history_conflict_check`：与上组同样的实际反馈，再给出通用建议：如果历史反馈和当前书面合同不一致，应核查来源而非直接沿用。它是带额外提示的开发策略，不能声称等信息或学习算法优越。
3. 使用无模型、公开输入的直接过滤计数做强简单对照；每组的最终输出都用同一冻结 T2 合同计数器评分，同时保留实际退出、原始文本和执行日志。分别报告反馈是否与 T1 合同发生冲突、T2 事实计数、输出合同、错误和成本。

若 T1 的原 checker 与合同 checker 一致，实验仍可比较历史与反馈类型，但**不称作已发生评分冲突**。每组 1 次，只作机制和流程诊断；同一底层文件/任务族不用于统计显著性或跨来源确认。不同 feedback arm 的额外文本及 token 不同，单次通过与否不能归因为某条经验。

## 运行与成本合同

固定已验收的 OpenCode、本地 Qwen3.6-35B-A3B 和受限 Docker；网络仅通过受限 UDS 代理访问本机研究模型，禁止联网下载、生产服务和 Memory 写回。每次最多转发 16 个 HTTP 请求、900,000 字节 POST 请求体、每步 8,192 输出 token、最长 600 秒；每个拒绝、超时、无输出、缓存读取和物理请求均记录。按顺序运行至多 6 个 episode，不并发占用模型；0 训练、0 付费 API。事后新增对照与修补必须另记并保留首轮结果。模型生成之前检查输入和 upstream 原测试 hash；结果按历史、任务、操作合同与最终答案分开分析。
