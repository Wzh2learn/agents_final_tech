## 3. Candidate design: skill applicability under change

The selected public prefix-cache task is a **static S3FIFO task**, not a naturally observed historical skill invalidation or version migration. Partridge is a real exposed commit pair but has no located historical agent `SKILL.md`; neither is valid independent evidence of a new adaptive-skill method. A changed prefix-cache policy/config can be constructed as a deliberately synthetic development control only, not claimed as a naturally observed deployment. For real confirmation, locate dated upstream skill/contract and independently sourced environment/version changes, with license, task semantics and executable verifiers.

Once a qualifying pool exists, compare the following with identical task instances, Qwen checkpoint, harness, environment, task/time/token caps, and public information access; record actual prompt lengths and verification calls rather than assuming identical cost:

| Arm | Skill / check availability | Purpose |
|---|---|---|
| no skill | task only; no hidden evaluator | Measure raw agent headroom. |
| fixed skill | same selected skill always available | Closest SkillsBench-style control. |
| full-current documentation | all admissible task-relevant docs available, equal tool access | Strong information-available baseline; cost measured, not assumed equal. |
| static/version or direct contract rule | same visible docs/metadata and equal allowed tool actions | Strong simple rule; commit identity and direct metadata should be tested, not version string only. |
| candidate conditional selection | same docs/metadata/actions, no hidden oracle | Test whether a deployable applicability mechanism improves end-to-end result at matched compute/information. |
| same-budget retry / fixed verification | same model, tool cap and accessible evidence | Check whether gains are just additional inference or verification. |

Skill exposure itself is the experimental variable: a no-skill arm intentionally lacks the skill text and is **not** an equal-information comparison. Main method claims instead require same accessible information and matched total compute against fixed-skill, static-rule and retry arms. Oracle and verifier remain unavailable to all agents. Hidden dataset solutions/test code and future commits cannot leak through mounts, prompts, skill descriptions, dependency caches, execution log or training. Disjointness must be by underlying source/workflow/version family, not question paraphrase; compare model release date to exposures and report uncertainty.

**Primary outcome:** task success with independent verifier; additionally track invalidation detection, stale-skill misuse, harmful or incorrect tool actions, false abstention, wall time, input+output tokens, external tool and verification costs. Report conditional performance on tasks where baseline agent is competent, not just raw score; cluster results by source family and include uncertainty. Freeze the contract and success criterion before held-out use. The main counterfactual is a static/equally informed rule at equal total cost; stop if it matches the candidate or if changed task outcomes are fully explained by deterministic metadata. Include an unchanged-environment control to detect over-rejection.

**Feasibility and blockers:** The offline checks justify preparing an isolated adapter, not launching a full model study. Resolve BenchFlow version and official task digest, oracle-vs-verifier independence, OpenCode/Qwen local agent adapter, safe resource caps, action/trace receipts, external dataset terms, complete source-family splits, and a second independently sourced natural version-change task. No budget is presented as actual spending; existing 2,000-trace replay and tests are CPU only, all model/agent/judge/training calls 0. The 1.1 GB third-party clone and generated Docker image are retained as user-visible local evidence, not silently removed.
