## 可执行候选：反馈与经验的适用性，而非又一个技能库

### 2026-11-05 补充：反馈演化与多次执行近邻

- [Rethinking Self-Evolving Agent Skills](https://arxiv.org/abs/2608.02636) 比较成功与失败反馈组合、多轮 skill 更新及推理时扩展，并在不同模型、任务、验证与迁移集合上报告效果。作者的主要实验包含 14 个模型—基准设置、42 条反馈运行，并报告 388 个候选中 55 个产生不同的验证最优版本；这是作者结果而非本项目复现。其[开源代码](https://github.com/HKUST-KnowComp/rethinkskill)有 MIT 声明，任务数据和执行依赖须单独核验。**影响**：失败反馈保留、多轮更新、验证选择及普通测试时重试都不是单独的新贡献；必须按同信息量和总成本比较，区分候选探索与迁移测试。
- [EvoSkill v2](https://arxiv.org/abs/2610.25931) 的作者使用可运行工具的有状态 evolver、每个训练任务多次尝试与训练／验证／最终测试隔离；研究全量反馈及通过／失败反馈，在表格和银行任务上报告质量与优化成本。作者以每个任务三次尝试分析运行噪声，并观察到单次验证选择可能错误拒绝候选。**影响**：有状态 Agent、工具辅助诊断和重复采样已有直接近邻；本项目优先检验实际可见的反馈状态如何进入后续任务及其适用边界，而不是把这些组件当成新方法。其论文结果尚未在 GB10 复现。

上述只是可检验的候选区别，不构成已证实的新颖性。建议下一批以真实轨迹为输入，比较完整历史、普通摘要、公开 meta-skill 风格抽取、透明状态保留规则，以及同信息量的候选方法；控制模型与执行预算，核对实际读取、源任务结果及跨来源迁移，并单列经验形成和验证开销。

探索问题：在真实工具任务**有限反馈、反馈可能不完整或有错、经验可迁移范围变化**时，能否依据运行中可见证据选择“直接执行、重试、验证、复用旧经验或暂缓更新”，减少后续回合的错误而不丢失已具备能力？目前只是研究假设；Skill-V、SEAL、SkillEvo 与 SkillShift 可能已覆盖关键机制，必须全文比对其做法后才能判断独立性。

2026-11-04 对 [EdgeBench 发布的任务定义](https://huggingface.co/datasets/ByteDance-Seed/EdgeBench/tree/be611b133201649458b2094e8e7af24d1ef0b064)做元数据资格筛查：51/51 项均声明 `linux/amd64`；本次实测 GB10 host 与 Docker 为 `aarch64`，系统未注册 x86 binfmt，`qemu-x86_64-static` 和 `proot` 均不在 PATH。含 51 项来源文件哈希的元数据回执保存在 GB10 `research_evidence/agent_learning_20261030/edgebench_platform_screen_20261104.json`，SHA-256 `ac5078c21c898ca08d7424becb965d7ee4cf6b38ef6fdc0d72cba014902ac738`。该结果只说明直接运行官方镜像需要先处理架构兼容；尚未测试镜像的其他架构、用户态仿真、另一机器或任务内容，不把它作为基准不可用的结论。官方还提供隔离工作/评分环境和可迭代反馈，值得对照反馈获取与长期学习的具体协议，但其 12 小时设置不等同我们当前短程开发面板。

进一步核对 [SkillFlow v1 附录 C.2](https://arxiv.org/html/2604.17308)：作者已经比较“完整历史上下文、无历史、持续维护 skill 库”，因此这三臂的对比本身不是新贡献；其单模型对照与我们的本地模型、工具读取及任务设置也不能直接比较数值。该版本的 C.2 正文写历史上下文完成率 `47.41%`，相邻 Table 6 写 `51.04%`，两者未在该处解释差异；在作者澄清或核对发布结果前不选取其中一个当作确定的复现目标。我们观察到的具体工具读行截断可作为需要控制的信息传递条件，但仅凭这一现象不能宣称超越 SkillFlow。

2026-11-04 补充比对上述近邻后，值得进一步实测的方向是：在经验可能随任务或环境变化而过期时，如何结合可见信息决定是否复用，以及**何时为这一判断额外付出执行和验证成本**。它是研究问题而非已证实的空白：SkillApt 已使用配对反馈并将证据获取成本列为后续问题；SelfEvoSkill 已研究配对审查与修订；Zep 已维护带来源的技能和准入。对照必须计入经验形成、任务执行、调用和验证成本，并包含始终验证、完全不验证、固定周期、随机及缓存等同预算策略；实际任务需要可独立核验的结果和不泄漏目标答案的经验来源。此前 Adaptive V3、exact-cache 以及现有对账强基线已解释的收益不能重复包装。

建议的可证伪实验采用连续任务序列，先分来源/版本，保留失败与成功实例。每轮同时记录任务成功与任务级回归、安全拒绝、经验是否被使用、反馈标签与工具轨迹、上下文及实验总成本。需同时比较：无历史、完整历史、固定窗口/检索、原任务 skill、普通 retry、SEAL 式固定外部验证/回滚、Skill-V 式适用过滤与历史回放，额外给同等可见信息的透明规则；我们的候选必须在独立序列或未见版本上，超越相应最强质量—成本基线或解释可复现的机制差异。不可把校准样本的模型自评当人工 gold；隐藏 reference 仅用于事后独立测量，非所有基线都默认可用。

**本项目已有可信起点**：[dialogue 研究](DIALOGUE_PILOT_RETURN_20261030.md)暴露 verifier 假阳性/误拒及同起点修复；[prefix 研究](PREFIX_FEEDBACK_RETURN_20261030.md)显示公开完整 skill 是强基线；[invoice 研究](INVOICE_AGENT_RETURN_20261030.md)中具体诊断有效，但一个给定相同诊断的确定性规则同样完全通过。它们支撑设计问题，不单独证明任何方法的普遍优势。下一步应优先从真实连续或环境变化基准中建立 2–3 个来源隔离的可运行序列，并根据实测调整训练或推理预算。相关论文所述结果是其作者报告，非本项目复现。

SkillShift 官方仓库和 GB10 架构的实际资格检查、官方 smoke 的一处检查冲突，以及可行的后续路径见 [SkillShift 资格记录](SKILLSHIFT_QUALIFICATION_20261030.md)。

2026-10-31 补充阅读 [RSE-Bench 方法正文](https://arxiv.org/html/2610.19910)：其 N-Bind 将真实 outcome 与同源另一执行记录错配，原任务目标和原评分规则保持不变；还区分学习时噪声与冻结后的部署评测。我们新发现的[金融检查器案例](FINANCIAL_FEEDBACK_CONTRACT_FINDING_20261031.md)涉及原 solution 的字符串拼接以及后续**人为明确新合同后旧检查器不再匹配**，与 N-Bind 的具体扰动入口不同，但“不同入口”本身不保证新颖性。后续若提出经验更新方法，应尽可能在 RSEClaw 可用时纳入其现有方法、干净历史、错配反馈和学习/评测分离；不能把一次静态上下文提示比较写成已学习技能。

2026-10-31 针对[依赖任务真实 skill 试验](DEPENDENCY_SCOPE_REPEAT_RETURN_20261031.md)补读近邻方法正文：

- [Skill-V §3.2–3.4 与附录 B.6](https://arxiv.org/html/2610.11781)已经把技能维护为可执行合同，对模型提出的修订做结构检查、历史证据 shadow replay、非回归门及适用过滤。因此“给 skill 加检查/回滚/适用条件”不是本项目可直接占有的新方法。
- [CoEvoSkills §3.3 与附录 C](https://arxiv.org/html/2604.01687)已经在 SkillsBench 上交替改进技能和代理验证器；其描述的代理验证器不读取生成器的技能源，只用任务、可见数据和产物构造测试，并在案例中报告过代理验证与 oracle 的偏差。我们可探索对**技能中的可执行片段及其外部状态副作用**直接构造证据检查，但这只是与其所述验证信息边界的具体比较，不等于该机制已新颖或有效；需要比较公开实现或明确标注的同信息预算近似。
- [CFOE §5](https://arxiv.org/html/2610.22984)已经比较从失败出发、加入 verifier 反馈与额外交互的迁移效果；我们的源轨迹包含失败和可见验证反馈，不能包装成其无反馈 cold-start 设置。RSE-Bench 的案例也已讨论错误归因与污染规则，故“失败导致错误经验”本身不是研究空白。

由本项目结果形成的**可检验候选问题**是：在相同可见信息和总预算下，能否把技能中的“可运行指令、从失败推断的条件、对证据/环境的副作用”拆开，用可执行见证或来源约束修订经验，同时保持变化任务完成率？需与普通执行重试、直接工具文档、CoEvoSkills/Skill-V 可复现部分、透明检查以及只增加交互次数的预算匹配对照比较；还要证明对不同来源和工作流的增益，而不是只修复一份 Trivy 文本。
