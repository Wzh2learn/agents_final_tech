# 经验迁移：统一扩大预算后的开发性敏感性检查

2026-10-31。此前两次目标执行中，生成 skill 两次交付所需身份，普通历史没有交付。为了检查这种差异是否受额度或随机执行影响，在看到这些结果之后，按[事前写入仓库的本次计划](DEPENDENCY_SCOPE_BUDGET_SENSITIVITY_PLAN_20261031.md)将每组的允许转发请求从 16 扩至 32、请求体总量从 0.9 MB 扩至 2.4 MB、墙时从 600 秒扩至 900 秒，各执行一次。任务、固定模型、冻结历史和生成 skill 未变；这不是独立来源、预注册确认或多种子检验。

| 条件 | 输出及原 verifier | 逐漏洞身份和阈值 | 物理转发 POST | 观察 |
| --- | --- | --- | ---: | --- |
| 无历史 | 无 CSV；0/8 | 无法评分 | 32 | 达到请求上限 |

`0/8` 表示没有输出时原测试的失败数，不是 8 个独立回答。生成 skill 的 1 项原测试失败来自输出的 Red Hat CVE 地址不同于原参考地址；未核验两条链接实际内容，不以域名差异直接裁定正确性。后验检查中，两个有输出的组给出的三个 CVSS 值均能在冻结扫描结果的至少一个来源中找到；这不证明 Agent 真正使用了哪个来源，也没有验证其他描述字段。[原始聚合](dependency_scope_budget_sensitivity_summary_20261031.json)记录每条输出、metadata 副本、哈希及接口账本；[聚合脚本](summarize_dependency_budget_20261031.py)复核每次 raw 的哈希和冻结历史/skill。

## 判断更新

普通历史也能产生目标结果，因此之前两轮的观察不足以证明生成 skill 相对原始历史有独特收益。普通历史这次使用 14 个请求，低于旧上限 16；即便新额度统一放宽，也不能单凭这一条成功把差异归因于额度或随机性，更不能据此下因果结论。原始历史和生成 skill 条件各自的信息长度、表述和模型路径不同，且只有一个已暴露任务来源。

两组有输出的 Agent 都修改了工作副本的数据库时间。原扫描数据库和原 metadata 未被修改，但错误的新鲜度叙述本身是经验可信性问题；不能把这两条输出称为完整可靠的交付。生成 skill 自带的示例代码在此前字面执行测试中漏掉全部源任务身份，而目标 Agent 最终没有原样使用它。这两项观察提出值得验证的问题：**如何既复用历史中的可执行步骤，又拒绝无证据的环境状态或错误代码？** 当前尚未证明一种方法可解决该问题。

## 成本与下一步

本批实际转发 **95 次 POST**、本地拒绝 **2 次**，step 回执报告 **1,420,783 tokens**，其中缓存读取 **1,295,129**；缓存读取不能按同量新 token 解释。与源任务、经验生成和前两次目标试验合计为 240 次转发、9 次拒绝、3,198,671 reported tokens，其中缓存读取 2,828,766。训练、付费 API、生产 Memory 写回为 0。各批原始轨迹位于 GB10 的 `research_evidence/agent_learning_20261030/` 下。

下一阶段应在独立公开项目和其他工作流上固定输入、显式分数来源规则、可执行检查和来源隔离，同时比较普通历史、未经修订的生成经验、带约束的经验和确定性工具基线。已经检查过漏洞数量的项目只作为开发集；证据不足时可以转向其他 Agent 经验与技能适配问题，不必局限在依赖扫描。任何新方法要与信息量和总成本相匹配的基线比较。
