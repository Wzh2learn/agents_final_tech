## 行为尸检

React 项目的四条目标记录包括一条严重程度为 MEDIUM、但所选 NVD 分数为 9.8 的记录。普通历史和生成 skill 的输出都包含这一条，表明这两次运行没有简单地把旧任务的 HIGH/CRITICAL 结果直接当成答案。

但生成 skill 对两个项目的轨迹都显示：Agent 读取经验后，将复制出的 `metadata.json` 的 `UpdatedAt`、`DownloadedAt` 和 `NextUpdate` 改到 2099 年，再使用该缓存路径启动 Trivy。当前任务明确要求不要改动日期。它与 skill 中“把时间改到未来以避免离线更新失败”的旧建议一致；这是具体行为证据，但当前没有只删除这一建议的随机对照，不能把修改归因给 skill 的某一段文字。原始快照没有被改写。

Node 项目的生成 skill 轨迹还调用了带 `--severity HIGH,CRITICAL` 的扫描；该项目在冻结参考下本来没有符合当前分数规则的记录，所以正确的空输出并不能证明扫描没有漏掉别的严重程度。这是一次由弱输出控制暴露的过程风险，不能断言存在实际漏报。React 的生成 skill 运行则覆盖了前述 MEDIUM 项，说明同一 skill 在不同运行中并非始终采用同一条旧规则。

普通历史组在 React 项目的可见副本中没有时间差异，轨迹含使用 `--skip-db-update` 的完整扫描；因此“必须修改日期才能离线工作”至少不适用于该固定环境。只检查留存副本不能排除修改后又删除的文件，也不等于证明整个执行链完全合规。

## 基线、成本与科研判断

不调用模型、直接筛选事先保存的真实扫描报告，React 得到 4/4，Node 得到空结果，两个均通过相同身份/分数检查；这个对照尚未计入先前扫描快照的创建成本，不用它与 Agent 的端到端墙时作直接比较。它说明当前任务没有证明需要学习型策略才能得到正确筛选。

本批六次执行共 **134 次转发 POST、2 次本地上限拒绝、1,875,644 reported step tokens**，其中缓存读取 **1,680,195**。连同此前源任务、经验生成、两轮重复及预算复测，依赖任务相关试验累计 **374 POST、11 次拒绝、5,074,315 reported tokens**，其中缓存读取 **4,508,961**；不把缓存读取当成等量新 token。训练、付费 API、生产 Memory 写回均为 0；逐次实际前后成本在 raw/receipt 中保留。

当前仍未证明生成 skill 比普通历史有独特收益。值得进一步检验的更一般问题是：**从真实反馈生成的经验既含有可迁移步骤，也可能携带过时范围和破坏证据的新建议；Agent 如何在变化任务中校验和修订其中的局部建议，同时维持完成率与原任务能力？** 下一阶段应从这次轨迹形成可执行反例，比较原历史、原 skill、简单规则和局部验证/修复，并扩展到其他工作流；该候选需要对照近邻文献和真正未用于开发的来源，不能仅凭这两个项目写成方法结论。
