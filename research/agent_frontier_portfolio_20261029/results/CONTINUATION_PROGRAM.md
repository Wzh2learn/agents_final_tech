## v2：实际学习规则

输入为既有程序、实际公开轨迹及完整续行成败。程序以`step(公开观察, JSON记忆)`发出工具调用/用户请求或交还Actor。隐私用户工具、私有状态、原始参考和未来任务不进入学习请求或Actor。

规则已实现为[effect_counterexamples / feedback_update_request](../continuation_program.py)：

1. 在同一处理函数上查找重复决策；比较前后工具返回字段。
2. 若字段已改变、存在中间未标错误的公开`new_<field>`回执，而该字段未出现于函数及非状态helper的静态读取足迹，将它列为编辑候选；无匹配就弃权。
3. 选首个候选，要求非空更新包含该函数；同信息普通编辑可自由选择位置。两者都最多改8个既有函数、可加纯helper、同模型/上限，均可弃权。
4. 接受与否由完整后续执行、原生结果及形成加执行成本决定。字段与读取足迹是定位启发式，不是因果责任证明。

这次自动定位到`node_data_usage`：工具返回的`data_refueling_gb`已由0变2、再变4，程序却仍用`used > limit`重复推销充值。继续检查官方原生环境发现额度判断含已充值量；**这是现有可见字段被忽略，不能只解释为缺少长期记忆。** 官方实现公式没有提供给任何writer。

HASP已有可执行动作干预和反馈演化；StateGraph已有依赖核验及动作重规划。该候选要检验的是上述反馈驱动编辑规则的额外收益，不能用程序化、记账或局部修订本身建立创新。详见[近邻表](../IJCNN_RELATED_WORK_REFRESH_20261030.md)。

## 主动找反例：有充值不等于额度已足够

新规则实际学成`refueled > 0`就跳过再次充值。用原生环境构造以下三个数量状态，并在隔离容器对同一处理函数作一步调用；期望标签未挂载给程序，0次模型请求：

| 公开数值：已用/套餐/已充值 | 原生额度仍不足？ | 效果条件程序选择 |
|---|---|---|
| 15.1 / 15 / 0 | 是 | 提议充值 |
| 15.1 / 15 / 2 | 否 | 转去检查漫游 |
| 17.1 / 15 / 2 | 是 | **仍转去检查漫游** |

这确定了已学条件的范围缺陷：读到相关字段不代表已经学对充分条件。它是构造状态上的强制函数诊断，不是完整Agent任务失败或已验证的跨任务结论。首次CPU准备因原生日期未序列化报错，按公开JSON日期格式修正，旧错误保留，未重发模型。
