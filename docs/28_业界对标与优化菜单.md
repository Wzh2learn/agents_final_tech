## 一、Agent 工作台（WorkBuddy / Manus / Devin / Cursor）

**他们怎么做**
- WorkBuddy: 三区（左任务列表+状态机 进行中/已完成/失败/待处理/规划中/已归档；中对话区实时展示执行步骤；右结果区 概览/产物/全部文件/变更 四视图）。
- Manus: 三栏但「聊天降格为输入口、工作台升格为主视图」；右侧=云端虚拟机屏幕级直播（浏览器滚动/填表/跑代码所见即所做）+ 动作流文字播报（搜索→打开→提取→写入）+ 步骤计数/耗时/阶段标签；长任务中透明过程=信任。
- Devin: 会话时间线 + 每步缩略图 + **可编辑 plan**（用户改计划再执行）+ 可恢复 session + PR/Slack 集成。
- Cursor: agent 每工具调用可见 diff + 命令审批 + 后台 agent（2025）。

**我们现状**: 单页纵排；stageRail 事后 chips；无任务概念/无状态机/无实时过程；M2 等待黑盒（route=on 当前≒直连回落）。任务二设计稿（docs/27）已对准 WorkBuddy/Manus 范式。

**gap**
- G1 执行过程实时可视化缺失 —— 设计稿方向 B 正面解决。工作量 1.5-2d（含在改版），价值 高（演示叙事核心）。推荐: 随任务二拍板。
- G2 任务状态机/可恢复会话缺失 —— 设计稿方向 A 的左栏+localStorage。1d，中。推荐: 二期。
- G3 plan 可视化/可干预 —— 我们 M2 链无"计划"概念（检索→生成固定流），当前规模不需要。0d。推荐: 不做，记原则（任务复杂度上升再议）。
- G4 产物一等公民化（Manus 右屏/WorkBuddy 产物视图）—— 我们的表格/勾稽/引用是面板而非"交付物"。含在改版右栏。推荐: 随改版。

## 二、RAG 问答（Perplexity / NotebookLM / Dify / Coze）

**他们怎么做**
- Perplexity: 编号内联引用 [1][2] + 来源 favicon；Pro 搜索把多查询分解过程可见（searching→reading→answering）；追问建议 chips。
- NotebookLM: 句级引用 chip，点击→来源卡片**原文段落高亮**；无答案时明确"sources 未提及"。
- Dify/Coze: 检索节点透明——top_k chunks+score 在编排画布可见可调（top_k/阈值配置面），调试与信任兼得。

**我们现状**: 答案带 sources（sample/table/field）+ 拒答规范 + 多轮；但引用不可点穿到段落、检索过程不可见、无追问建议（场景 B 在台账）。

**gap**
- G5 引用→原文段落高亮: 需 chunk 级定位（sources 已有 sample/table，缺 chunk 文本回显）。1d，中高。推荐: 改版二期或独立小项。
- G6 检索透明面板: 把 knowledge_search 的 top_k+score 直接展示（数据已在返回里，纯前端）。0.5d，高。推荐: **最优先小项**。
- G7 拒答升级候选选择题 = docs/26 场景 B（已设计）。2d，中高。推荐: 按台账触发条件（场景 A walkthrough 认可后）。
- G8 追问建议 chips: 0.5d，中。推荐: 菜单。

## 三、文档解析/表格识别（Docling / MinerU / LlamaParse / TextIn）

**他们怎么做**
- Docling (IBM, MIT): 布局 DocLayNet + **TableFormer 结构识别——只认结构不读文字**（输入表格图像裁剪，输出行列/合并结构+单元格 bbox，文字映射回原生文本层，避免 OCR 污染结构）→ DoclingDocument → MD/JSON。
- MinerU (上海AI Lab): 布局+表格+OCR 流水线，中文强，输出 markdown。
- LlamaParse: agentic/LLM 表格提取，schema-guided。
- TextIn (合合): 商业，中文金融单据强。

**我们现状**: 文本层规则解析 + pymupdf 坐标重建 + vision-8004 OCR(markdown prompt) + HTML 提取；scenario1 门禁 15/15。

**gap**
- G9 无专用表格结构模型: 复杂表头/合并单元格靠规则+坐标，上限受限（TraFax 传真件部分可救）。全量引入 2-3d，中高（视甲方样本复杂度）。推荐: 等样本驱动。
- G10 Docling/MinerU ARM64 可行性探针: torch 依赖在 GB10 有卡死前例（PaddleOCR SIGSEGV / VLM Triton gcc），但 Docling 模型可走 ONNX/CPU。0.5d 结论型。推荐: **先探针，结论入台账**。
- G11 借 TableFormer「结构与内容分离」思路改 VLM prompt: 第一遍只输出表结构（行列数/表头），第二遍按结构填值。0.5d，中。推荐: 低成本可试。

## 四、RAG eval（RAGAS / DeepEval / TruLens）

**他们怎么做**
- RAGAS: faithfulness = 把答案拆成 claims 逐条对 context 核验（防整体打分漂移）；另有 answer_relevancy / context_precision。
- DeepEval: G-Eval（CoT judge + 归一化）+ **pytest 原生断言**（metric >= threshold 进 CI）。
- TruLens: groundedness 等 feedback 函数 + 面板。

**我们现状**: 确定性 16/16 + AI judge 四维 0-5（整答级，:8004 temp=0）；judge 一致性未测（今晚 Phase 2 补）。

**gap**
- G12 数值 claim 确定性核验: 我们领域数值密集，可**不靠 LLM**——抽答案数值（千分位容差）逐条对检索 chunk 文本核验，比 RAGAS 的 LLM 拆 claim 更硬。0.5d，高。推荐: **今晚做（Phase 2）**。
- G13 judge 一致性: 今晚测，结果入台账。
- G14 eval pytest 原生化: run_eval.sh 包成 pytest 断言。0.5d，中。推荐: 菜单。
