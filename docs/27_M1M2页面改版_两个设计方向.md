## 1. 背景与设计输入

**任务来源**：甲方交付后的 M1/M2 页面改版 + 处理过程可视化（M1 流水线步骤、M2 agent 链路进度）。设计先行，拍板后才动代码。

**参考系**：腾讯 WorkBuddy（codebuddy.cn/work）。已核实的参考要点：
- **三区结构**：左侧任务列表（按空间分组，卡片显示标题/状态/更新时间；搜索+筛选；置顶/重命名/归档）；中间对话区（任务标题栏 + 消息流 + **执行过程实时展示** + 输入区 + 可中断）；右侧结果区（概览/产物/全部文件/变更 四视图切换）。
- **任务状态机**：进行中 / 已完成 / 失败 / 待处理 / 规划中 / 已归档。
- **执行过程叙事**：理解需求 → 规划步骤 → 执行操作 → 交付成果，对话区实时展示关键步骤与进度；任务内可追问、携带上下文。

**用户设计锚（必须满足）**：
1. 左：任务列表 = 解析任务 + QA 会话，带状态徽章
2. 中：执行过程分步可视 = M1 六步流水线 + M2 agent 链路步骤条（**等待变过程**）
3. 右：产物面板 = 表格 + 勾稽 + 引用证据
4. 任务栏模式切换：直连/验证链路、精确/AI 辅助
5. 风格：浅色商务 + 蓝色主色 + 8px 圆角 + 高密度分区

**现状盘点**（src/web/templates/m1.html + m1.js/m1.css，197+913+1120 行）：
- 单页纵排：topbar → status-band（stageRail **事后**渲染 chips，非实时）→ metricGrid → control-strip → 三面板（表格/KV/复核）→ M2 QA 面板 → 对比面板；schema 与建议映射均为 modal。
- 已具备的构件可复用：`#stageRail` 阶段轨、`#suggModal` 建议映射选择题（docs/26 场景 A）、`#preciseParseChk` 精确解析开关、`#reconcileSection` 勾稽。
- 缺口：无任务概念（单会话单页）、无实时分步进度、M2 链路等待无过程反馈、建议映射藏在 modal 里。

**API 约束（红线）**：两方向只消费现有端点，不改任何 API：
`/api/m1/parse-file`、`/api/m1/schema*`、`/api/m1/schema-suggestions*`、`/api/m2/ask`、`/api/m2/products`、`/api/m2/compare*`、`/api/health/full`。
⚠ 已核实：`/api/m2/ask` **不支持每请求 route 覆盖**（M2_OPENCODE_ROUTE 为全局 env）。模式切换的诚实设计见 §4.2。

**流水线步骤定义（两方向共用）**：
- M1 六步：① 上传与预处理 → ② 版面分析/OCR → ③ 表格检测 → ④ 字段映射 → ⑤ 勾稽校验 → ⑥ RAG 入库
- M2 验证链路五步：① 问题理解 → ② RAG 检索 → ③ 重排 → ④ 答案生成 → ⑤ 独立复核与引用
- **诚实规范**：现有 parse/ask 均为同步单次调用，无逐步事件。实时步骤条用**客户端时间轴动画**（时长按实测基线标定：直连 QA ~2s、parse 非 OCR <2.1s、OCR 10-90s、agent 路 15-20s），并在 UI 上以"过程示意"标注；真实步骤事件流（SSE）为可选二期扩展，不在本次范围。

## 2. 方向 A：三栏任务工作台（WorkBuddy 正传）

```
┌──────────────────────────────────────────────────────────────────────┐
│ 顶栏 48px  品牌 | 当前任务标题 | [直连|验证链路][精确|AI辅助] | ● 服务状态 │
├───────────┬──────────────────────────────────────┬───────────────────┤
│ 左 240px  │ 中：执行流                             │ 右 380px 产物面板  │
│ 🔍搜索    │ ┌ 任务标题栏（状态徽章 + 耗时）       │ Tabs:             │
│ 解析任务  │ ├ 步骤消息流：                        │ 表格 | KV | 勾稽  │
│ ● 嘉合05 ✓│ │ ① 上传预处理 ✓ 0.3s               │ | 引用 | 建议映射②│
│ ● 华泰 ✓  │ │ ② 版面分析 ✓ 1.8s [vision-8004]   │                   │
│ ● TraFax ✓│ │ ④ 字段映射 ✓ 93.8% · 2条建议 →    │ 建议映射 tab:     │
│ ◐ LU 进行中│ ├ QA 气泡：问→答（带引用 chips）     │ 候选勾选+应用/拒绝│
│ QA 会话   │ │ 验证链路步骤条（复核中 ⟳ 12s）     │ + 回归门禁反馈    │
│ ● 嘉合问答│ ├────────────────────────────────     │                   │
│ ○ 持仓对比│ │ 输入框（追问 / 新指令）             │                   │
└───────────┴──────────────────────────────────────┴───────────────────┘
```

**配色**（浅色商务）：主色 `#2563EB`，底色 `#F5F7FA`，卡片 `#FFFFFF`，分隔 `#E5E9F0`，正文 `#1F2937`，次文 `#6B7280`，成功 `#16A34A`，警告 `#D97706`，失败 `#DC2626`，进行中脉冲 `#2563EB`。圆角 8px，正文 13px，行高紧凑。

**关键交互文字稿**：
1. **任务即上下文**：每次上传解析或发起 QA 即生成一个任务卡（标题自动取文件名/问题摘要），入左栏"解析任务"/"QA 会话"组；点击任务卡，中栏恢复该任务完整执行流（历史存 localStorage，不加后端存储）。
2. **解析过程**：Run 后中栏逐条点亮六步卡片；每步完成显示耗时 + 关键指标（③ 表数、④ 命中率、⑤ 通过项）；点击步骤卡展开细节（未映射列、勾稽明细）。OCR 样本在 ② 显示"视觉模型读图中…预计 N 秒"+ 进度条。
3. **建议映射不再用 modal**：④ 出现建议时，右栏"建议映射"tab 亮徽章；勾选应用后中栏追加一条消息"已应用 2 条映射 → 回归门禁通过 → TraFax 命中率 71.2%→x%"，失败回滚同样以消息呈现（可见性是 T4 验收要求）。
4. **QA 双链路**：直连路答案气泡直接出现（~2s）；验证链路先在气泡顶部展开五步步骤条，逐步点亮，等待期文案"独立 agent 正在复核答案与引用…"；完成后答案 + 引用 chips（点击引用 → 右栏切到"引用"tab 高亮来源段）。
5. **状态徽章**：进行中（蓝，脉冲）/ 已完成（绿）/ 失败（红）/ 待处理（灰，用于有建议未确认的任务）。

**优势**：与 WorkBuddy 心智一致，甲方"任务管理"预期直接命中；多任务切换自然；建议映射/规则配置从 modal 升为一等面板。
**代价**：改造面最大（任务上下文管理 + 三栏骨架 + 流式渲染，JS 重写约 60%）；单屏信息分区多，1366×768 需压缩布局。
**工作量估算**：2.5–3 人天。

## 3. 方向 B：流水线画布控制台（演进式）

```
┌──────────────────────────────────────────────────────────────────────┐
│ 顶栏 44px  品牌 | 任务下拉 ▾ | [直连|验证链路][精确|AI辅助] | ● | 🗂任务抽屉 │
├──────────────────────────────────────────────────────────────────────┤
│ 流水线画布（本页主角，横向六节点，连线渐变=进度）                          │
│ ①上传 ── ②版面/OCR ── ③表格检测 ── ④字段映射 ── ⑤勾稽 ── ⑥入库        │
│ ✓0.3s    ✓1.8s        ✓5表        ✓93.8%⚠2建议  ✓4/0/0   ✓12chunks   │
│ （节点可点 → 下方展开该步细节抽屉；④ 抽屉内嵌建议映射选择题）             │
├────────────────────────────────┬─────────────────────────────────────┤
│ 控制台（55%）                  │ 产物面板（45%）                      │
│ 文件拖放区 + Run + 精确解析☑   │ Tabs: 表格 | KV | 勾稽 | 引用        │
│ 实时日志流（时间戳滚动）        │ 表格 tab: 标准化表格缩略 + 展开      │
│ QA 输入 + 多轮对话（紧凑）      │ 勾稽 tab: 通过/跳过/失败分组        │
└────────────────────────────────┴─────────────────────────────────────┘
（QA 验证链路时，画布切换为五节点 agent 链：理解→检索→重排→生成→复核⟳12s）
```

**配色**（科技商务蓝，与 A 略区分）：主色 `#1677FF`，画布底 `#F7F9FC` + 细点阵网格，卡片白，状态色与 A 相同色板。圆角 8px，13px。

**关键交互文字稿**：
1. **流水线是主角**：任何解析任务的过程 = 看六节点逐个点亮。进行中节点显示 spinner + 实时秒表（等待变过程）；完成节点定格耗时与关键指标。节点间连线按进度着色。
2. **节点抽屉**：点击节点在画布下方展开该步细节（④ = 未映射列 + 建议映射选择题，直接内嵌，不用 modal）；再点收起。建议应用后节点徽章变化 + 回归门禁结果以 toast + 日志流双通道反馈。
3. **任务切换轻量化**：顶栏任务下拉（最近 8 个）+ 右侧任务抽屉（完整列表 + 状态徽章，需要时拉出，不常驻）——比 A 的常驻左栏省空间，弱于 A 的多任务体验。
4. **QA 双画布**：直连路不启用画布，对话区直接出答案；验证链路启用五节点画布，等待期 = 看 agent 链逐步推进，"独立复核"节点停留时间最长并显示已耗时，讲清"为什么慢"。
5. **日志流**：控制台保留滚动日志（时间戳 + 事件），给想看细节的人；与节点画布互补（宏观 vs 微观）。

**优势**：演示叙事最强（甲方一眼看到"系统在做什么"）；与现有单页结构偏差最小（演进式，JS 改造约 35%）；选择器保留最容易；等待体验最好。
**代价**：多任务并行管理弱（抽屉化）；"任务列表"锚点被弱化（以任务下拉 + 抽屉补偿，不如 A 正统）。
**工作量估算**：1.5–2 人天。

## 4. 公共规范（两方向共同遵守）

### 4.1 状态徽章与色彩
进行中=主色脉冲 / 已完成=绿 / 失败=红 / 待处理=灰 / 警告（有建议未确认、勾稽有失败项）=琥珀。徽章统一 20px 高、圆角 10px、12px 字。

### 4.2 模式切换（诚实设计，重要）
- **精确/AI 辅助**：已具备（`#preciseParseChk` → `?llm_fallback=0`），做成 segment 开关，语义不变。
- **直连/验证链路**：后端当前为全局 env 开关（M2_OPENCODE_ROUTE），**不支持每请求覆盖**。因此 segment 组件做成**状态指示 + 只读**：显示当前生效链路与预期延迟（"直连 ~2s"/"验证链路 15-20s"），hover 提示"链路由服务端配置，如需切换请联系运维"；不做假交互。若未来要真切换，需给 M2AskRequest 加可选 route 字段（记入台账，需另行拍板，属 API 变更）。

### 4.3 空态 / 加载 / 错误
- 空态：画布/执行流空时给引导文案"上传一份对账单，或点 Sample 载入示例"；产物面板空时"解析完成后，表格与勾稽结果会出现在这里"。
- OCR 加载：步骤 ② 文案"视觉模型读图中…（本地推理，约 N 秒）"+ 不定长进度条。
- 错误：统一顶部居中 toast（4.5s 自动消失，失败类需手动关闭可点 ×）；解析失败任务徽章变红，步骤流定格在失败步并给出原因。

### 4.4 建议映射选择题（承接 docs/26 场景 A + T4 实现）
交互不变：候选列表（原列名/建议标准字段/置信度/理由）+ 勾选 + 应用所选/拒绝所选 + 应用后自动跑 scenario1 回归门禁，命中率下降自动回滚。**改版只改容器**（modal → A 的右栏 tab / B 的节点抽屉），`#suggList/#suggApplyBtn/#suggRejectBtn` 语义保留。

### 4.5 选择器保留映射（视频脚本与测试的命脉）
record_demo_video.py 实际使用：`#fileInput` `#m2Question` `#m2AskBtn` `#m2NewChatBtn`。
测试与 walkthrough 相关：`#tableCount` `#reviewBadge` `#kvCount` `#runBtn` `#sampleBtn` `#preciseParseChk` `#suggBtn` `#suggCount` `#suggApplyBtn` `#reconcileSection` `#unmappedSection` `#confirmBtn` `#m2ChatLog` `#m2Meta` `#cmp*`。
**规则**：实现 PR 必须保留上述全部 ID（可换容器，不可改名）；确需移动的在 PR 描述中附旧→新映射表，且 tests/test_web_integration.py、test_m1_schema_suggestions.py 必须全绿。

## 5. 方向对比与推荐

| 维度 | A 三栏工作台 | B 流水线画布 |
|---|---|---|
| 与 WorkBuddy 一致度 | 高（正传三区） | 中（借鉴状态机+过程可视化，布局自创） |
| "等待变过程"体验 | 好（步骤消息流） | **最好**（画布逐节点点亮 + 秒表） |
| 多任务管理 | **强**（常驻任务列表） | 弱（下拉+抽屉） |
| 演示叙事 | 好 | **最好**（一眼看到系统在工作） |
| 改造面 / 工作量 | 大 / 2.5–3 人天 | 中 / 1.5–2 人天 |
| 选择器保留难度 | 中（容器重组多） | 低（演进式） |
| 1366×768 适配 | 需压缩三栏 | 天然适配 |

**推荐**：**先 B 后 A**。B 作为一期落地（演示叙事优先、改动小、风险低、甲方演示尽快可用）；A 作为二期演进目标——在 B 的基础上把任务抽屉升级为常驻左栏即收敛为三栏工作台。两个方向不冲突，B 是 A 的子集路径。若甲方明确"多任务管理是刚需"，也可直接上 A。
