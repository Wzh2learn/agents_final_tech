# GB10 本地模型服务两阶段实施计划与分工

## 1. 项目目标

本计划面向 M1“业务规则文档结构化抽取”和 M2“业务规则知识库问答”两项任务，利用 NVIDIA GB10 开发机完成本地开源模型的部署、任务适配、效果评测和 API 服务化。

最终形成一套与现有 AI Model/Agent 系统松耦合的模型能力：模型侧独立迭代，系统侧只通过统一 API 调用，不直接依赖模型权重、推理框架、Conda 环境或 GB10 的具体部署方式。模型替换、量化和微调不应引起上层业务代码大范围修改。

本计划只承诺模型实验、量化结果、稳定服务和必要的界面演示；复杂 Agent 编排、企业系统集成和生产化改造在模型候选收敛后由工程集成负责人承接。

## 2. 总体技术边界

```text
现有业务页面 / Agent 系统
          |
          | 固定请求与响应协议
          v
模型适配层（模型名称、任务模板、JSON Schema）
          |
          | OpenAI-compatible API
          v
GB10 模型服务（llama.cpp / vLLM / 专项推理服务）
          |
          +-- M1：文本模型、OCR/VLM、结构化输出
          +-- M2：Embedding、Rerank、生成模型
```

统一暴露健康检查、模型列表和推理接口，生成模型优先兼容 `/v1/chat/completions`。上层系统通过 `base_url`、`model` 和任务协议切换本地模型与外部 API。

GB10 具有 121 GiB 统一内存，资源使用按“轻量基线、主力候选、质量上限”分层：4B/8B 用于快速开发，14B Q4 作为日常主力候选，Qwen3.6-35B-A3B Q4 作为质量上限对照。开发机一次只常驻一个待测生成模型；OCR/VLM、Embedding/Rerank 和表格模型按任务离线运行，避免多个大模型争用统一内存。

## 3. 第一阶段：数据集、模型调优与数字结果

建议周期为 4 周，目标是回答“GB10 上哪套模型方案最适合 M1/M2，以及调优是否产生了可验证收益”。

### 3.1 建立任务数据集

1. 从脱敏业务文档中整理 M1 标注集，覆盖字段、条件、阈值、动作、来源和异常样例；
2. 建立 M2 问答集，包含标准答案、证据片段、无答案问题和角色化问题；
3. 固定训练集、验证集和测试集，测试集不参与 Prompt、LoRA 或检索参数调节；
4. 建立数据版本、标注规范和人工复核记录，保证模型结果可复现。

第一版建议至少包含 100 条 M1 样例和 100 条 M2 问答；数据不足时优先保证覆盖面和标注一致性，不用重复样例凑数量。

### 3.2 建立基线并逐层调优

1. 使用已部署的 Qwen3-4B、8B、14B 和 Qwen3.6-35B-A3B 跑同一测试集，并用现有外部 API 模型作为参考对照；
2. M1 先优化 Prompt、JSON Schema、字段校验和失败重试，再评估 8B/14B 的 LoRA/QLoRA；
3. M1 文档解析对比 PaddleOCR-VL、MiniCPM-V 和 Qwen3-VL，测量 OCR 错误对规则抽取的影响；
4. M2 对比 Qwen3-Embedding、BGE-M3、Qwen3/BGE Reranker，并调节 chunk、Top-K 和上下文构建；
5. 对每项改动做单变量对照，记录模型、量化方式、参数、速度、峰值内存和失败样例；
6. 只有当轻量微调相对 Prompt/RAG 基线产生稳定收益时，才保留微调权重进入服务候选。

### 3.3 评价指标与阶段验收

| 任务 | 核心指标 | 第一阶段建议验收目标 |
| --- | --- | --- |
| M1 结构化抽取 | JSON 合法率、Pydantic 通过率、字段 Precision/Recall/F1、人工修正率 | JSON 合法率不低于 98%，Pydantic 通过率不低于 95%，字段 F1 相对未调优基线提升不少于 5 个百分点 |
| M2 检索 | Recall@K、证据 Top-K 命中率、Rerank 增益 | Recall@5 不低于 90%，并报告 Rerank 前后差值 |
| M2 回答 | 答案准确率、来源命中率、无证据拒答率、人工评分 | 来源命中率不低于 85%，无证据拒答率不低于 90%，综合质量相对基线提升不少于 5 个百分点 |
| 工程性能 | 首 Token 延迟、生成速度、总耗时、峰值内存、连续运行稳定性 | 在 GB10 上完成重复测量，候选模型连续完成整套测试且无服务崩溃 |

绝对阈值在首轮标注一致性检查后可调整一次，调整原因必须写入实验记录，不能依据最终测试结果倒推指标。

### 3.4 第一阶段交付物

- M1/M2 数据集说明、脱敏样例、标注规范和数据划分；
- 可重复运行的 Benchmark 脚本及原始结果；
- 基线、Prompt/RAG 调优、可选 LoRA/QLoRA 的对比表；
- 外部 API 与 GB10 本地模型在效果、延迟、资源和数据可控性方面的对比结论；
- GB10 资源、速度和效果的 Pareto 分析；
- 一个主力模型服务和一个轻量备选服务；
- OpenAI-compatible API、启动脚本、健康检查和调用示例；
- 模型选择结论、限制条件和失败样例报告。

## 4. 第二阶段：界面验证、服务固化与工程交接

建议周期为 2 周。模型探索结果只做必要的界面效果展示，不在本阶段重新建设完整平台。

### 4.1 最小演示闭环

复用现有系统页面和接口，形成三个演示视图：

1. M1 页面：上传或选择文档，展示抽取字段、规则、来源、置信信息和校验状态；
2. M2 页面：输入业务问题，展示回答、引用片段、来源文档和无依据拒答；
3. 模型实验页面：展示基线与调优后指标、延迟、资源占用和典型成功/失败样例。

界面用于证明模型能力和实验结论，不把权限、多租户、复杂工作流和生产运维纳入模型侧验收。

### 4.2 服务固化与交接

1. 冻结推荐模型、推理参数、Prompt/Schema 版本和评测数据版本；
2. 固化 API 请求、响应、错误码、超时、日志和健康检查约定；
3. 提供服务启动、停止、切换模型和回滚命令；
4. 提供 M1/M2 联调样例、验收用例和已知限制；
5. 由工程集成负责人在此接口之上完成 Agent 调优、业务 Prompt、流程编排和企业系统接入。

第二阶段完成的标志是：现有页面能够调用 GB10 模型服务展示 M1/M2 结果，工程集成负责人无需理解模型环境和权重细节即可按接口文档完成后续开发。

## 5. 分工与责任边界

### 5.1 角色 B：模型与数据负责人

负责 GB10 环境、模型下载与部署、M1/M2 数据集、模型基线、Prompt/结构化约束、检索与重排实验、可选 LoRA/QLoRA、量化与性能测试、模型 API、数字结果和最小界面验证。角色 B 对“模型能否稳定提供可量化能力”负责。

不负责企业系统内部重构、复杂 Agent 工作流、生产权限体系和长期业务运维。

### 5.2 协作同学：Agent 与工程集成负责人

负责在候选模型冻结后完成 M1/M2 Agent 编排、业务 Prompt 深化、工具调用、会话与状态管理、现有系统适配、前后端联调、企业接口对接、异常降级、权限与部署运维。该角色对“模型能力如何进入企业现有系统并形成稳定业务流程”负责。

### 5.3 共同确认事项

双方在第一阶段开始时共同确认输入输出 Schema、测试数据口径和验收指标；在第二阶段开始时共同完成 API 联调、Demo 脚本和交接验收。任何业务接口变更通过版本化协议处理，避免模型实验与 Agent 工程互相阻塞。

## 6. 已有基础与近期动作

目前 GB10 开发机已完成 Qwen3-4B/8B/14B/35B 的 OpenAI-compatible 服务基线，四个脱敏连通与格式样例均通过；Qwen3-Embedding、BGE-M3 和 BGE Reranker 已完成离线冒烟测试；PaddleOCR-VL、MiniCPM-V、Qwen3-VL、TabFM 和 TabPFN 已完成下载或基础环境准备。上述结果证明技术链路可行，但不能替代正式业务数据集上的质量结论。

近期优先事项是完成数据授权与脱敏、扩充 M1/M2 标注集、锁定评价脚本，然后在 8B、14B 和 35B 上形成第一张有语义质量意义的对比表。网络恢复后再补齐需要 Hugging Face 授权的 TabPFN v3，不影响 M1/M2 主线启动。

## 7. OpenCode 与 MCP 路线补充

Agent 集成采用“OpenCode + 现有 JinRongAgents RAG MCP + GB10 本地模型服务”，不再为主线新建 Knowledge RAG/ChromaDB 或 RAGFlow 知识库。

1. 现有 `RAGService`、PGVector、BM25、来源追溯接口和知识库页面是唯一知识底座；
2. 新增薄 MCP Adapter，将检索、来源读取、M1 解析和评测能力以任务级工具提供给 OpenCode；
3. OpenCode 负责主 Agent、子 Agent、权限和模型路由，不保存业务文档和索引；
4. GB10 模型通过 OpenAI-compatible API 独立迭代，14B 为日常主力，35B 只用于困难样例复核；
5. 第一阶段先完成 M2 只读检索闭环，再增加 M1 OCR、规则抽取和 Pydantic 校验；
6. 多 Agent 编排在单 Agent 工具调用稳定后开展，避免过早增加调度复杂度。

详细实施和验收标准见 `docs/09_OpenCode与现有RAG_MCP实施方案.md`。
