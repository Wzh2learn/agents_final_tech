## 0. 背景与终态

交付终态 = OpenCode harness + GB10 本地模型 + 多 agent + MCP + skill。2026-08-05 已完成交付链端到端验证（见 `docs/experiments/2026-08-05_opencode_e2e.md`）：

- OpenCode 1.18.3 经 `opencode.json` 的 gb10 provider 驱动 :8004 上的 Qwen3.6-35B-A3B（本地模型，无外部 API）
- 三个本地 MCP（jinrong-rag / jinrong-vision / jinrong-tabular）协议级 smoke 全过，vision 经 :8004 mmproj 实测推理成功
- 五个 agent（m2-qa / m1-extraction / evidence-verifier / tabular-researcher / tabular-runner）权限隔离配置就位并端到端跑通
- skill 层经 `skills.paths` 注册仓库 `skills/` 目录

当前页面后端是 :5050 FastAPI 单体（UI + /api/m1/* + /api/m2/*），甲方演示随时可用。**本文档决策的是：页面后端如何（以及是否现在就）切到 OpenCode 链。**

## 1. 路线 A：FastAPI 网关模式（渐进）

:5050 保持唯一入口与现有 UI 不变；FastAPI 内部把部分端点的实现从"进程内直调"改为"调用 OpenCode agent"。OpenCode 以 `opencode serve`（headless HTTP server）作为 sidecar 常驻，FastAPI 通过其会话 API 派活给指定 agent，把 agent 产出（JSON/文本）映射回现有响应结构。

**切换粒度示例**
- `/api/m2/ask` → 派给 m2-qa（带引用回答），响应结构不变，前端无感
- `/api/m1/parse-file` → 保持确定性 parser 直调（性能敏感，不走 agent），复核/解释类增量功能走 agent
- 新增"交叉验证/审计"类端点 → evidence-verifier

**工作量**：中（约 2-4 天）
1. opencode serve sidecar 的启动/守护/健康检查（复用 deploy/ 现有 supervisord 方案，不启用 systemd）
2. FastAPI 侧一个薄适配层：会话创建 → 发消息 → 轮询/流式收结果 → 结构映射 + 超时与重试
3. 每个迁移端点的回归测试（对照现有响应）

**风险**：低-中
- 两跳延迟：agent 链路比进程内直调慢（单轮 ~10s 量级 vs <1s），只适合迁移本身容忍秒级延迟的端点
- :8004 单 slot 并发瓶颈：页面请求与 agent 推理共享一个模型服务，需限流或排队
- sidecar 生命周期管理（崩溃重启、会话堆积清理）

**优势**：演示面零改动，可随时灰度/回滚（端点级开关），甲方无感。

## 2. 路线 B：OpenCode 原生入口 + 独立可视化

放弃 FastAPI 作为页面入口：用 OpenCode 原生界面（`opencode web`）或自研薄前端直连 opencode server API 作为交互入口；现有三面板 UI 改造为独立的只读可视化页面，数据来自 agent 会话产出与 PG 持久层。FastAPI 单体缩容为纯数据服务或废弃。

**工作量**：大（约 1-2 周）
1. 前端交互重建：上传/解析/问答/复核全部改走会话式交互（或自研前端对接 opencode server API）
2. 多用户/认证重新设计（OpenCode server 原生是单用户工具，甲方多人访问需要网关或会话隔离）
3. 演示脚本、docs/19/20/23 全套交付文档重写
4. 确定性快路径（parse-file <2.1s）如何保留的设计

**风险**：高
- 演示能力回归风险：甲方演示链路整体重排，验收前不宜动
- 会话式交互对"上传文件→看三面板"这类确定性流程是体验降级
- OpenCode 版本耦合加深（UI 与行为随上游版本变化）

**优势**：架构最接近终态，无双层 API 包装，agent/skill/MCP 能力直接暴露给使用者。

## 3. 对比与建议

| 维度 | A：FastAPI 网关 | B：OpenCode 原生入口 |
|---|---|---|
| 工作量 | 中（2-4 天） | 大（1-2 周） |
| 演示回归风险 | 低（UI 不动，端点级灰度） | 高（整体重排） |
| 延迟影响 | 迁移端点变慢（秒级），快路径保留 | 全流程会话化，快路径需专门设计 |
| 与终态距离 | 中（仍有 FastAPI 层） | 近 |
| 回滚成本 | 低（端点开关） | 高 |
| 甲方感知 | 无感 | 交互方式大变 |

**推荐：先 A 后 B。** 现阶段先按路线 A 把 m2-qa 一个端点做灰度试点（影响面最小、价值最直接：答案带引用已由 agent 链验证），跑稳后再逐端点迁移；路线 B 作为甲方验收并确认交付形态后的演进方向。若甲方明确要"OpenCode 原生交付"，则直接评估 B，但需接受演示重建周期。

**已拍板（2026-08-05）**：
1. 路线 A 保底 + 路线 B 为目标，先 A 后 B
2. 首个灰度端点 = `/api/m2/ask`（A2；开关须待 embedding 两步落地后开）
3. sidecar = opencode serve :4096（tmux opencode-serve 直启，2026-08-05 已起并 smoke 通过；supervisord 为生产化备选）

## 4. 执行路径梳理（2026-08-05 拍板）

### 4.0 前置：embedding 切本地（不属于 A/B，但阻塞两条路线）

现状：SILICONFLOW_API_KEY 缺失 → vector+BM25 系统级降级，:5050 与 MCP 检索都走 fallback+本地 bge-reranker（RAG QA 14/15 为降级态成绩）。用户决策：**不恢复云端 key，走本地 embedding**。

事实核查（2026-08-05 实测，只读）：
- 代码路径已就位：`vector_store.py:get_embeddings()` 优先读 `LOCAL_EMBEDDING_MODEL_PATH` → `LocalSentenceTransformerEmbeddings`（SentenceTransformer 适配器），无需云端 key。
- 本地模型已就位：`~/wzh/models/hf/qwen3-embedding-0.6b`，与云端 `Qwen/Qwen3-Embedding-0.6B` 同权重、SentenceTransformer 兼容。PG 存量语料 764 向量（m1_parsed_statements 137 + tat-dqa 627 + knowledge_base 0）全部 1024 维、由该云端模型生成。
- CUDA 路径不可用：torch 2.13+cu130 在 ARM64 上 Triton JIT 编译失败（缺 Python.h，与 Qwen3-VL safetensors 同根因）；**走 CPU**：加载 2.8s，编码 2 条查询 226ms。
- 向量空间对齐验证：本地编码两条测试查询对存量语料 top-1 均命中正确 chunk（嘉兴民安总资产 0.564 / 复熙混合25号资产总值+币种 0.587）→ 同模型替换，**无需重新 ingest**。

执行步骤：
1. 远端 `.env` 追加 `LOCAL_EMBEDDING_MODEL_PATH=/home/testuser/wzh/models/hf/qwen3-embedding-0.6b` + `LOCAL_EMBEDDING_DEVICE=cpu`（rerank 已有 CPU 设备先例，config 里 rerank.device=cpu）。
2. MCP 链立即生效：`start_mcp_server.sh` 已加载 `.env`，下一次 opencode 会话的 knowledge_search 即有 vector+BM25（不重启任何服务，零风险）。
3. :5050 生效需重启以载入 env：**红线例外，显式确认后执行**；窗口约 10-30s，重启命令与原启动命令一致（uvicorn main:app --workers 2）。
4. 验证：/api/health/full embeddings 计数 >0；RAG QA 15 题（目标 ≥14/15，预期改善）；MCP 与 :5050 检索交叉一致。

不选 bge-m3 的原因：与存量 764 向量空间不一致 → 必须全库重灌，且历史基线全部基于 Qwen3-Embedding；同模型替换 = 零迁移。

## 4.3 B4 对等验收排期提案（2026-08-06, 基于 A2 灰度实测）
