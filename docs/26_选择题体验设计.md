# 26_选择题体验设计

> 状态: 活跃 | 更新: 2026-08-09 | 取代/被取代: 无
> 设计理念（用户原话）：我们有 opencode + 多 agent + MCP + skill + OCR + 视觉模型这么多手段，要给用户的是一张**选择题**——把用户没想到的也解析出来端给他。甲方对映射 schema 是递进式理解和完善的，我们要主动提供这种可能。

## 一、设计原则

系统已经会做很多事，但甲方能感知到的只是"上传 → 出表 → 问答"。选择题体验的目标：**把系统的判断、发现、能力以"供选择"的方式端到甲方面前**，让甲方永远处于"确认/勾选"的位置，而不是"学习/配置"的位置。

三条原则：
1. **不做填空题，做选择题**：系统先算出候选，甲方只做选择（可拒绝、可修改，但永远从零选项开始）。
2. **递进式完善可见**：每次选择都让下一次更好，且提升幅度看得见（命中率 delta）。
3. **异常永远有出口**：建议错了可以拒绝，拒答了可以换候选，链路超时自动回落。

## 二、场景 A：映射候选选择题（本轮实现）

### 2.1 已有基础

- 解析时未映射列 → 本地 35B LLM 兜底映射 → 结构化建议写入 `config/schema_suggestions.json`（sample/table/raw_column/standard_field/置信度/理由/样本值，自动去重）——schema 自学习闭环已建成（2026-08-08）。
- `scripts/m1_apply_schema_suggestions.py` 已实现批量应用（校验 → 写 schema → 回归门禁拦截错误建议）。
- schema 写操作热加载（下次 parse 即生效，无需重启）。
- 实证案例：华泰紫金扫描传真 42.9% → 100%（8 个账号上下文字段沉淀为规则，fax/HTML 样本普涨）。

### 2.2 产品形态："建议映射"面板

位置：/m1 页面新增"建议映射"入口（规则配置旁），点开为模态框：

```
┌─ 建议映射（系统自动发现，等待您确认）──────────────┐
│ ☑ [高] 分红方式 → 分红方式                          │
│    理由: 列名与候选标准字段完全一致                  │
│    出现于: sample_20260506_233222LU.pdf · 交易对账单 │
│    样本值: 红利再投资                                │
│ ☐ [低] 产品代码 → 产品名称                          │
│    理由: 代码非名称本身（建议人工确认）              │
│    [改为其他字段 ▾]                                  │
│ ─────────────────────────────────────────           │
│ [应用所选]  [拒绝所选]        应用后自动复测命中率    │
└──────────────────────────────────────────────────────┘
```

字段：原列名 / 建议标准字段（可下拉改选其他标准字段 = 手改出口）/ 置信度徽章（高中低）/ 理由 / 出现样本与表 / 脱敏样本值。

### 2.3 甲方第一次见到的操作动线

1. 上传一份新版式对账单 → 解析完成，命中率显示（如 70%）
2. 复核面板出现黄色提示："发现 N 条映射建议" → 点击打开面板
3. 浏览建议：高置信度默认勾选，低置信度默认不勾选
4. 点"应用所选" → 系统写入映射规则（热加载）→ 提示"规则已生效，请重新解析该样本查看提升"
5. 甲方重新上传同份样本 → 命中率提升可见（70% → 95%）
6. 下次遇到同版式新样本：直接高命中，无需再次选择——**递进式完善闭环**

### 2.4 异常出口

| 异常 | 出口 |
|------|------|
| 建议错误 | 取消勾选 / 点"拒绝所选"（进入 rejected 名单，不再重复建议） |
| 建议对但目标字段不对 | 下拉改选其他标准字段（手改出口） |
| 应用后命中率反而下降 | 回归门禁自动拦截（下降超差的建议拒绝写入）；已应用的可在"规则配置"里删除该近义词 |
| 建议列表为空 | 面板显示"当前无待确认建议"，不打扰 |

### 2.5 API 设计（最小集）

- `GET /api/m1/schema-suggestions` → 未处理建议列表（含 rejected 过滤）
- `POST /api/m1/schema-suggestions/apply` body `{items: [{raw_column, standard_field, table}]}` → 写 schema（admin token 同现有 schema 写保护）→ 返回 `{applied, skipped, hit_rate_delta_hint}`
- `POST /api/m1/schema-suggestions/reject` body 同上 → 移入 rejected 名单

### 2.6 与 m1-gap-triage skill 的关系

m1-gap-triage 是**工程侧 SOP**（agent 用）：0 表/高 unmapped → 读原文诊断 → 补 synonyms → 回归门禁 → 报 delta。建议映射面板是**甲方侧产品化**：SOP 的"诊断"（步骤 1-2）仍由系统/agent 完成，"补词 + 验证 + 报 delta"（步骤 3-5）变成甲方点一下。两者共用同一数据管道（schema_suggestions.json + 回归门禁），不重复建设。

## 三、场景 B：问答候选选择题（设计先行，实现评估后定）

### 3.1 现状与目标

现状：检索不到 → "根据现有对账单数据，未找到相关信息"（诚实但到此为止）。
目标：拒答升级为"未找到 X，但该产品/文档有 A、B、C 字段可用，您是否想问……"——把库里实际有什么端给甲方。

### 3.2 候选从哪来

1. **实体定位**：从问题中提取产品/样本实体（复用现有 _extract_product 逻辑）
2. **字段清单**：该实体已入库 chunk 的 standard_fields metadata + 解析记录的表头清单（不需要新索引，读现有 cmetadata 即可）
3. **排序**：问题词与字段名的字符重叠度 + 字段在库中出现频次（高频字段优先）
4. **防噪音边界**：
   - 最多 3 个候选
   - 仅在"检索无证据或拒答"时出现（正常回答不附加，避免干扰）
   - 候选必须来自与问题实体相关的文档（不跨产品乱推）
   - 数值类问题优先推数值字段，名称类问题优先推名称字段（类型感知）

### 3.3 示例

> 问：复熙混合25号的基金经理是谁？
> 答：根据现有对账单数据，未找到"基金经理"相关信息。该产品在库中可用的字段包括：**资产总值、币种、证券代码、市值、对账日期**——您是否想问其中某项？

### 3.4 实现位置与工作量评估

- 直连路：m2_service 拒答分支收集候选（读 cmetadata，~1h）+ 答案拼装（~0.5h）+ 测试（~0.5h）= **约 2h**
- agent 路：playbook 加一条拒答契约（m2-qa 二次检索字段清单）——依赖 agent 路稳定性，二期再做
- 结论：若本轮时间允许则实现直连路最小版；否则设计入库、台账排期（见 memory/THREADS.md）

## 五、验收标准（本轮最小闭环）

1. 建议映射面板在 /m1 可见：列出 schema_suggestions.json 未处理建议（含置信度/理由/样本值）
2. 勾选 → 应用 → schema 热加载 → 重新解析同一样本命中率提升可见
3. 拒绝 → 建议不再出现
4. 手动改选目标字段可用
5. 场景 B 按评估结果：实现或台账排期
