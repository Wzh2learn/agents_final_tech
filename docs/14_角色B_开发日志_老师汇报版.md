# 角色 B 开发日志：GB10 本地模型与 M1/M2 联合闭环

**汇报状态：2026-07-28（含真实甲方对账单业务对齐）**

## 一、工作目标与技术路线

本阶段目标是在不改造现有 JinRongAgents 核心业务的前提下，利用 NVIDIA GB10 开发机探索适合 M1/M2 的开源模型能力。M1 负责金融 PDF、扫描件和表格的 OCR、版面恢复与规则结构化；M1 产物进入现有知识库后，M2 完成检索、重排、证据问答和无证据拒答。两者被统一为“文档解析 -> 建库 -> 问答”的联合任务，而不是两个独立演示。

系统保持松耦合：现有 Web、FastAPI、`RAGService`、PGVector/BM25 和来源追溯是唯一知识底座；GB10 模型通过 OpenAI-compatible API 或受控 MCP 工具接入；OpenCode 负责 Agent 调度，不另建第二套知识库。

## 二、阶段工作时间线

### 1. 项目迁移与远程开发基础

- 将迁移资料归档到仓库，建立 `docs/`、`models/`、`scripts/`、`HANDOFF.md` 和 `AGENTS.md` 等协作入口。
- 完成 Windows 本机到 Linux GB10 的 VS Code Remote-SSH 工作流，并在开发机建立 `~/wzh/projects`、`~/wzh/models`、`~/wzh/datasets` 和 `~/wzh/logs`。
- 采用 Git 作为本机与开发机的主同步方式；遇到本机 HTTPS reset 时，使用 Git bundle 将提交安全转移到开发机，再由开发机推送。
- 复用并隔离已有环境：`wzh_vllm`、`wzh_retrieval`、`wzh_vision`、`wzh_tabular`，避免为单项实验破坏共享 CUDA/Torch 依赖。

### 2. GB10 模型资源与基础验证

- 生成模型：Qwen3 4B、8B、14B 和 Qwen3.6-35B-A3B GGUF 完成四条脱敏格式样例验证，均为 4/4；14B 被选为 OpenCode/MCP 日常主力路径，35B 仅作质量上限对照，一次原则上只常驻一个生成模型。
- 检索模型：Qwen3-Embedding-0.6B、BGE-M3、bge-reranker-v2-m3 完成离线冒烟；Qwen3-Reranker-0.6B 已下载并完成后续固定中文样例排序验证。
- 视觉模型：PaddleOCR-VL-1.6、MiniCPM-V-4.6、Qwen3-VL-8B 在同一公开中文报纸图片上完成独立推理。冷启动耗时分别为 73.842、20.122、299.215 秒，峰值 CUDA 分配约 1.934、2.909、5.592 GiB。该结果只证明模型可运行，不是 OCR 质量排名。
- 表格模型：独立 `wzh_tabular` 环境中，TabPFN v2 与 TabFM 完成合成小样本 GPU 推理；模型链路可用，但尚无真实业务准确率。TabPFN v3 涉及授权与独立研究安排，不影响主线。

### 3. OpenCode 与 MCP 接入

- 复用现有 `RAGService` 实现只读 Knowledge MCP：`knowledge_search`、`knowledge_get_source`、`knowledge_list_collections`。
- 配置 GB10 Qwen3-14B provider，以及 M1、M2、证据校验等逻辑 Agent。配置存在不等于多 Agent 已完成。
- 定位并修复 OpenCode 子进程继承输出描述符导致的“任务已结束但 SSH 看似超时”问题；正式只读稳定性验收 20/20 通过，相关 focused tests 为 19 passed、6 个弃用警告。
- 增加隔离的 Vision MCP 与 Tabular MCP。Tabular MCP 的 TabPFN v2、TabFM 合成调用分别约 0.912、0.616 秒；专用 `tabular-runner` 可自动选择工具并约 26 秒完成整条 OpenCode 调用，其中模型推理约 1.013 秒。主协调器自动委派子 Agent 仍未验证。

### 4. M1/M2 联合数据方案

- 调研后选定 TAT-DQA 作为首个主数据集。它提供金融 PDF、带坐标解析、问答、计算过程与证据映射，许可证为 CC BY 4.0，适合同时评估 M1 和 M2。
- 固定 `joint-v1`：seed `20260722`，100 份文档、500 道问题。官方 train/dev/test_gold 严格映射到自定义 train/validation/test，文档为 60/20/20，问题为 300/100/100。
- 2026-07-23 验证结果：span 154、spans 78、arithmetic 154、counting 55、comparison 59；文档级和官方来源 split 泄漏均为 false；focused tests 9/9 通过。
- 7/7 官方文件已经取得，总计 1,514,773,595 字节；四个 JSON 可解析，dev/test/train 三个 ZIP 的 CRC 与成员检查全部通过。训练 archive 曾在 516,964,298 字节处中断，加入 HTTP Range 断点续传后完成。

### 5. 首个真实 M2 validation 基线

- 将 20 个 validation 文档的 627 个官方解析块通过 `RAGService` 写入隔离 collection，Embedding 使用 GB10 本地 Qwen3-Embedding-0.6B，不调用外部 Embedding API。
- 在 100 个 validation 问题上得到：文档 Recall@5 0.81、证据块 Recall@5 0.50、证据 MRR 0.4132、Qwen3-14B 答案 EM 0.24、正确证据引用率 0.48、平均端到端 3.079 秒，结构化 JSON 错误 0/100。
- span EM 为 0.4048，count 为 0.3636，arithmetic 为 0.0938，multi-span 为 0。50 题未在前五块命中正确证据；命中证据的 50 题中仍有 32 题回答错误。
- 该实验绕过 OCR/PDF 解析，是 M2 的“解析无损上限”，不是 M1 或完整端到端结果；test split 仍未使用。

## 七、2026-07-28 真实甲方业务对齐与 M1 资产归位

### 1. 真实 M1 业务（更正先前理解）

甲方真实样本（对账单 PDF/TXT/DOCX、组合证券 XLSX、解析表规则截图）表明，M1 的核心不是
“从自由文本抽取业务规则”，而是**对账单/报表解析 + 表头近义词映射**：各家券商/基金表头列名
不统一，M1 需解析表格、识别表头、用“标准字段→近义词”映射表（如 产品名称↔基金名称/账户名称/
产品全称/证券简称）把源列对齐到标准字段，并提取表头信息区键值对，输出标准化记录供 M2 做数据
分析问答。先前 `m1_service.py` 中文正则基线与 TAT-DQA 上的 LLM 抽取原型均非直接解此题，但各自
沉淀了可复用资产（见下）。

### 2. 先前 M1 资产归位（均有效，非弯路）

- **契约层**（`m1_service.py`）：Pydantic schema、流水线 stage、确定性 ID、M2 载荷、schema 校验
  过滤误报——作为解析结果校验层保留，新解析器输出同样过这套 schema 与 stage 可视化。
- **展示层**（`m1.html`/`m1.css`/`m1.js`）：四面板工作台、stage rail、metric grid、人工复核按钮、
  M2 载荷 copy/download——交互骨架与“证据链展示 + 人工兜底”范式已定型，后续改造为对账单解析
  工作台（左上传、中标准化表+映射命中高亮、右复核 unmapped 字段与数据分析入口），数据模型由
  ExtractedRule 换为 StatementRecord，前端范式不变。
- **LLM 兜底**（`m1_llm_extract_prototype.py`）：zero-shot 结构化抽取在英文财务文档可行（5/5、
  平均 9.8 指标/文档、JSON 一次解析 100%、需 `/no_think`），定位为复杂/无表头/未映射表格的兜底
  与交叉验证，而非第一遍解析（21.5s/文档，适合离线或难例）。
- **OCR 结论**：TAT-DQA 为数字原生 PDF（字符重叠 99.9%），OCR 非该集瓶颈；甲方真实扫描件仍需
  Vision MCP/OCR 验证，保留该路径。
- **多 Agent 骨架**（`opencode.json`）：已定义 m1-extraction / m2-qa / evidence-verifier /
  tabular-researcher 并配好权限，正是“多 Agent 确保解析正确”的现成骨架，先前未跑通只因缺真实
  解析引擎与真实样本，现已补齐。

### 3. 与“多轮解析 + OpenCode skill + 多 Agent + 数据分析 + 主模型 GB10”思路的对齐

该思路与现有架构高度吻合，落地为分层解析：(1) 第一遍确定性近义词映射（快、可解释，覆盖规整
表格）；(2) 第二遍 LLM 兜底 unmapped/低置信/无表头例，封装为 OpenCode 的 m1-extraction skill/
工具；(3) 第三遍证据/勾稽校验，由 evidence-verifier 承担，且对金融对账单优先用**算术勾稽硬约束**
（明细市值之和=合计金额、币种一致、日期格式）而非纯语义自审；(4) 标准化表上的数据分析问答由
m2-qa / Tabular MCP 承接；(5) 编排与最终回答用 GB10 默认模型（qwen3.8-max-preview / glm-5.2），
重活按需调专用模型/skill。
