# M1 规则抽取基线验证

日期: 2026-07-28
方法: 确定性文本规则基线（正则 + Pydantic），无模型推理、无 OCR
数据: TAT-DQA validation(dev) split 前 5 份文档（详细表）＋全 274 份 dev 文档（汇总）

## Scope

本实验验证 M1 展示工作台的确定性规则抽取基线（`src/biz/m1_service.py`），
不经过 OCR/VLM，不启动任何模型推理服务。test / test_gold split 全程未触碰，
仅使用 dev(validation) split。

- Dataset: TAT-DQA, CC BY 4.0
- Split: validation (dev) only；test split sealed
- M1 service: `src/biz/m1_service.py`（确定性正则 + Pydantic 校验）
- 单元测试: `tests/test_m1_service.py`（18 项）
- HTTP 端点: `src/web/routers/m1.py`（`/api/m1/sample`、`/extract`、`/review`）

数据结构勘误（影响脚本适配）：官方 `tatdqa_dataset_dev.json` 是
**question-centric**，每条为 `{doc: {uid, page, source}, questions: [...]}`，
其中 `block_mapping` 仅引用 block ID，**不内嵌文档段落文本**。真正的文档解析
文本块位于 `tatdqa_docs_dev.zip` 内的逐文档 JSON `dev/{uid}.json`，结构为
`pages[].blocks[].text`（block 无 `type` 字段，本实验取 `text` 非空的 block）。
任务模板中的 `doc.get("pages")/block.get("type")` 假设与实际不符，已据此适配。

## PDF 文本提取（Phase 3）

前置条件核查：

- 项目 venv **无** PDF 库（`pdfplumber` / `PyMuPDF(fitz)` / `pdfminer` 均未安装）。
- `raw/` 下**无解压的 PDF 文件**，仅有数据集 JSON 与 docs ZIP。
- 按任务字面条件，本阶段判定为 **BLOCKED**。

Best-effort 补充（不改变上述判定）：系统解释器 `/usr/bin/python3` 预装 PyMuPDF，
故从 `tatdqa_docs_dev.zip` **内存读取** `dev/{uid}.pdf`（dev split、只读、不落盘、
不触碰 test），提取文本后与官方解析 JSON 文本做字符重叠率对比：

| 文档 ID | 来源 PDF | 官方解析字符 | PDF 提取字符 | 字符重叠率 | 词 Jaccard |
| --- | --- | ---: | ---: | ---: | ---: |
| 4d41ea7a63b2 | quicklogic-corporation_2019.pdf | 2418 | 2416 | 0.999 | 0.984 |
| 2eb8a980ff3b | vodafone-group-plc_2019.pdf | 1019 | 1017 | 0.998 | 0.973 |

结论：官方解析文本与源 PDF 直接提取的字符重叠率约 **0.999**，词 Jaccard 约
0.97–0.98。TAT-DQA 为数字原生 PDF（非扫描件），官方解析高度保真，OCR 保真度
对本数据集并非瓶颈。

## 发现与限制

1. **M1 契约稳固**：18 项单元测试与 4 个 HTTP 端点全部通过；规则 ID 确定性可复现；
   Pydantic schema 校验、流水线 stage、M2 载荷结构均按约定工作。
2. **确定性基线不泛化到英文语料**：该基线是面向中文金融业务规则的脚手架
   （`规则一/触发条件/执行动作` 等模式）。在英文 TAT-DQA 10-K 叙事文本上，
   全 274 份 dev 文档抽取规则数为 **0**。这符合预期——基线定位为流水线与契约
   验证，而非该语料的生产级抽取器。
3. **schema 校验有效过滤误报**：候选检测器会在英文标题行上触发候选，但因
   触发条件/引用为空被 Pydantic 正确拒绝（每份文档 `校验失败=1`、`规则数=0`），
   未产生噪声规则。
4. **OCR 非 TAT-DQA 瓶颈**：官方解析与源 PDF 字符重叠 ~99.9%（数字 PDF）。
   这与项目对「M1 OCR 质量」的总体担忧形成对比——真实扫描业务文档仍需 OCR/VLM
   验证，但 TAT-DQA 本身不存在 OCR 保真度问题。
5. **对 M1/M2 闭环的启示**：要在 TAT-DQA 上推进 M1 业务指标，需要
   (a) 语言/领域适配的抽取方法（VLM/LLM 而非中文正则），或 (b) 改用中文业务规则
   文档语料。当前基线仅验证管线与 schema 契约；formal M1 业务指标仍依赖
   owner 批准的 label-to-source 映射与人工标注（与 HANDOFF 一致）。

限制：

- 完整 `src/main.py` 未在本环境整体启动（缺数据库依赖栈），M1 端点通过挂载真实
  路由的独立 harness 验证；其余 DB 相关路由未测。
- Phase 3 在项目 venv 内为 BLOCKED；best-effort 结果来自系统解释器的预装
  PyMuPDF，仅覆盖 2 份文档。
- 详细表仅取前 5 份文档（按任务要求），并以全 split 汇总补充代表性。
