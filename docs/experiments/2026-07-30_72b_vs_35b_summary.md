## Headline finding: latency

72B took ~248 s vs 35B ~17 s per structured extraction on GB10 (unified memory, Q4). The 72B is
roughly 14x slower, which makes it impractical for online M1 extraction on this hardware; the 35B
is the practical local LLM-extraction engine if an LLM-extraction path is used at all. Note that
the hardened rule-based M1 parser (m1_statement_parser.py) is the primary M1 engine and needs no
LLM, so LLM extraction is an alternative path, not the baseline.

## On the strict_json column (harness limitation, NOT a model verdict)

Both models returned non-strict-JSON under this harness even with /no_think and fence stripping.
Diagnosis: this is a harness / chat-template limitation (Qwen3 thinking-mode interaction on these
llama.cpp builds; /no_think alone did not force raw JSON; the answer likely lands in prose or in
reasoning_content), NOT a statement about model extraction capability. The raw model outputs are
retained at ~/wzh/p2_raw_72b_vs_35b.md for in-person inspection. Forcing strict JSON needs
thinking-disable tuning (e.g. server-side --chat-template-kwargs enable_thinking=false, or parsing
reasoning_content, or a stricter constrained-decoding / schema prompt), which is qualitative prompt
engineering best done in an interactive session. Therefore the only valid quantitative conclusion of
this bounded run is the latency gap above; an extraction-quality comparison is deferred to that
interactive tuning session.

## Safety / lifecycle

72B was loaded only for this bounded run and terminated immediately after (port 8006 freed, process
gone). No overnight-resident 72B. Launch was gated on MemAvailable > 50 GB; llama.cpp mmaps weights
so the resident 35B on :8004 was not memory-pressured.
