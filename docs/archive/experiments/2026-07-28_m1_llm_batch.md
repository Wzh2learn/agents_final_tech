## 对 M1/M2 闭环的结论

### LLM 抽取作为 M1 路径的可行性评估

**高度可行。** 核心发现：

1. **JSON 输出稳定性极佳**: 190/190 (100%) 直接解析成功，无需任何 fallback。
   `/no_think` 前缀 + `temperature=0` 组合确保 Qwen3-14B 输出完全确定性的合法 JSON。
2. **结构化抽取质量良好**: 97.4% 文档成功抽取 key_metrics，平均 7.85 个指标/文档，
   96.3% 文档抽取到 reporting_period。
3. **公司名抽取受文本截断限制**: 47.9% 的非 null 率主要因为 3000 字符截断后
   公司名称不在可见文本中。若增加截断长度或使用文件名元数据补充，可显著提升。
4. **零失败率**: 无超时、无 HTTP 错误、无解析失败，服务稳定性完全满足批量需求。

### 与确定性基线的互补关系

- **确定性基线**（`m1_service.py` 文本规则）: 快速、零延迟、可解释，但只能抽取
  显式模式匹配的字段，无法理解语义上下文。
- **LLM 抽取**: 能识别语义级别的财务指标（如 "Long-term care insurance reserves"），
  抽取 reporting_period 和 risk_factors 等需要理解的字段，但需要 ~19s/文档。
- **互补策略**: 确定性基线作为快速筛选和校验层，LLM 抽取作为深度结构化层。
  两者结果交叉验证可提升 M1 -> M2 数据质量。

### 下一步建议

1. **不需要 SFT**: 当前 zero-shot 效果已足够好（100% JSON 成功率），
   SFT 的边际收益不足以证明其成本。
2. **提升公司名抽取率**: 将文件名元数据（source 字段）作为额外上下文注入 prompt，
   或将截断长度从 3000 提升到 5000 字符。
3. **完成剩余 84 份文档**: 利用 checkpoint 断点续传，再运行 ~30 分钟即可完成全量。
4. **M2 标注对齐**: 将 LLM 抽取的 key_metrics 与 M2 问题类型对齐，
   评估结构化数据对 QA 准确率的提升。
5. **延迟优化**: 考虑将 `max_tokens` 从 1024 降到 512（当前平均 completion 仅 391 tokens），
   或增加 llama-server 的 batch size。
