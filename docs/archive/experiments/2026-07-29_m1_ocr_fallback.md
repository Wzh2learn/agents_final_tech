日期: 2026-07-29
方法: 本地视觉模型一次性 OCR（用完即停）→ 复用 `m1_statement_parser` 近义词映射
模型: PaddleOCR-VL-1.6（`~/wzh/models/hf/paddleocr-vl-1.6`，0.9B，输出含 markdown 表格）
数据: `~/wzh/m1_samples/` 中两份纯图样本（项目外，未入库；本报告全部脱敏）
脚本: `scripts/m1_ocr_render.py`（渲染/抽图）、`scripts/m1_ocr_fallback.py`（OCR）、`scripts/m1_ocr_map.py`（映射+记录）

## 结论先行

- **OCR 通路存在且下游映射器就绪**，但**在 GB10 上以整页可读分辨率跑 PaddleOCR-VL，无法在实用单页预算内完成真实对账单表格的 OCR**，故本轮 OCR→映射命中率为 **0/7**，闭环**未**在硬件/预算维度达成。
- 0 命中由两类原因构成，均非映射器缺陷：
  1. **整页表格 TIMEOUT**（3/7）：域内对账单表格（PDF 整页 + 两张 UI 截图表格）在 30s 与 180s 两档预算下均超时——GB10 上 PaddleOCR-VL 自回归解码约 14–18 字符/秒，整页表格输出量超出预算。
  2. **域外文本**（4/7）：`xinhua.docx` 实为**混合文档**，能在预算内 OCR 的 4 张图是 POC 需求说明文字（非对账单），不含对账单字段，故映射 0；且**启发式表头检测未产生任何误报表格**（0 假阳性）。
- **合成自检证明闭环本身可用**：喂入一张合成 markdown 对账单表，解析+映射 **7/7 命中**（`证券持仓明细`），表头区 KV 也正确抽出。即「若 OCR 能交付表格，映射器即可闭环」——瓶颈在 OCR 吞吐与样本地域，不在映射器。
- **是否纳入主线**：建议作为**门控兜底**纳入，但**不能以整页 OCR 现状直接上线 GB10**。需满足下列任一条件后再激活（见「建议」）。

观察:
- 能在预算内完成的都是**小尺寸/短文本**图（域外 POC 文字）；**域内整页表格在 180s 仍超时**。

喂入合成 markdown 对账单表（表头用真实近义词 + 一行表头区 KV），验证「OCR 若交付表格，映射器即闭环」：

## 对北极星指标「未知表头 / 无文本层冷启动」的贡献

- **未知表头**：映射器+OCR 表解析已就绪（合成 7/7），近义词表无需为 OCR 特调；待有真实 OCR 对账单文本后再据 unmapped 扩 synonyms（本轮无域内 OCR 文本，故无可学习项）。
- **无文本层冷启动**：通路**存在**、下游**就绪**，但**整页 OCR 在 GB10 上不满足单页预算**——状态应记为「**ready to activate, not throughput-viable on GB10 at full-page resolution**」，**不可**记为「已验证闭环」。
- 样本口径勘误：`xinhua.docx` 主要是 **POC 需求文档**，仅部分截图为对账单表格；它**不应**计入「对账单 OCR」分母。后续应把纯图样本拆为「域内对账单扫描」与「域外截图」两类分别度量。

## 建议（是否纳入主线）

纳入为**门控兜底**，但激活前需满足其一：

1. **表格/区域裁剪**（推荐，最契合现状）：先定位表区与表头 KV 区，按 crop 分别 OCR；每个 crop 尺寸小、输出短，可落入 30s 预算。本轮超时皆因整页喂入。
2. **更快解码**：更小/量化 OCR 模型，或更快 GPU；当前 GB10 统一内存带宽受限，0.9B 模型仅 ~14–18 字符/秒。
3. **异步/批处理**：把 OCR 移出同步单页预算，后台批跑后回填映射。
4. **样本治理**：拆分纯图样本域标签；为域内对账单扫描补「同源文本/人工标注」以计算真实 OCR→字段 F1。

不推荐：单纯降低分辨率换取速度——整页表格在默认可读分辨率（≈1M 像素）已接近可辨下限，再降将糊化表内小字，得不偿失。
