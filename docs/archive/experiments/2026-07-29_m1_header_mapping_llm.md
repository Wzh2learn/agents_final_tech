## 0. 流水线

1. **Phase 0 收集 unmapped**: `m1_statement_parser.py --dump-unmapped` 只读收集各样本 unmapped 源列 + 前 3 个脱敏样本值，按 (归属 schema 表, 列名) 去重。
2. **Phase 1 LLM 建议**: 对每个去重列串行调 Qwen3-14B，给标准字段清单 + 现有 synonyms + 列名 + 样本值，仅输出 JSON 建议。
3. **Phase 2 勾稽把关**: 对 confidence≥0.7 的建议，临时并入 schema **副本**（内存 deepcopy，不改原文件）重跑 parser；若某样本勾稽 pass→fail 或新增静默错配嫌疑 → 判有害拒绝。
4. **Phase 3 报告**: 安全建议汇总为「待人工确认 schema 补丁」，**不自动写回**。

去重 unmapped 列共 **32** 个（39 次表级出现的去重结果；基线 unmapped 总计 39 列）。

## 3. 勾稽拦截的有害建议（LLM 不能裸信）

本轮无 confidence≥0.7 的真实建议触发勾稽 pass→fail——LLM 对持仓明细的语义边界较克制（如把 `在途数量` 建议为 NEW 字段，而非误配到 `持仓数量`）。

**把关机制自检（反事实）**: 故意注入一条朴素规则常犯的错误建议 `证券持仓明细/配号 → 持仓数量 (故意有害·反事实)`，勾稽门拦下（新增嫌疑: sample_jiaxing_minan_20231031.pdf: 静默错配嫌疑新增「持仓数量←配号(含'配号')」）。证明该门确实能识别「映射成功但语义错误」，并非橡皮图章。

**勾稽盲区（更需人审）**: 嘉兴样本的成交流水/基金申赎/配号子表多为**仅表头、rows=0**，勾稽无数据可校验，对这些表的建议即便置信度高也**无法被勾稽证伪**。这正是「冷启动建议必须人审」的硬理由——勾稽只能把关有数据的表。

**启发式误报与把关修正**: 解析器的「静默错配嫌疑」只看源列名是否含关键词（在途/配号/冻结/质押/担保）。若 LLM 建议新增同名标准字段（如 `NEW:在途数量`），映射 `在途数量←在途数量` 语义自洽却被该启发式误报为嫌疑。把关层用 `_is_true_mismatch` 过滤：仅当**标准字段名本身不含该关键词**时才判为真错配，否则视为误报放行。本轮据此把 `NEW:在途数量` 从「误拦」纠正为「采纳」。

**无害但无增益**: 以下建议安全但不降 unmapped（目标标准字段已被更优近义词占用，贪心竞争落败）:

- `资金资产汇总/证券市值` → 资产市值 （conf=0.9）：该标准字段已被其他源列占用，新增 synonym 不改变贪心结果。

- **未知表头冷启动**: 从「人工逐列补映射」升级为「LLM 批量建议 + 勾稽自动把关 + 人审回写」，本轮对 32 个去重未知列自动产出建议，其中 15 条通过勾稽安全门。
