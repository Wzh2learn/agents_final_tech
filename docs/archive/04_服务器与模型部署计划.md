# 04 服务器与模型部署计划

## 1. 目标

在实验室开发机或 GPU 服务器上部署 30B 以内或 30B 左右可量化运行的本地模型，通过 OpenAI-compatible API 提供统一调用接口，支撑 M1 规则抽取、M2 RAG 问答、评测 Harness 和后续模型实验。

## 2. Remote SSH 开发方式

当前推荐开发方式：

1. 使用 VS Code Remote SSH 连接开发机；
2. 在远程开发机上 clone 项目仓库；
3. 在远程终端运行后端、前端和模型服务；
4. 通过 GitHub 同步代码；
5. 通过 `.env` 配置模型服务地址和 API key；
6. 由 Codex 辅助生成代码、脚本和实验工具。

注意：

- 不要把服务器密码写入仓库；
- 不要把 IP 写入仓库；
- 不要提交 `.env`；
- 只提交 `.env.example`；
- 系统级安装命令执行前需要人工确认。

## 3. 服务器环境摸底

## 4. 推理框架选择

### 4.1 vLLM

定位：主力推理服务框架。

适用场景：

1. 本地模型服务化；
2. 多用户并发调用；
3. OpenAI-compatible API；
4. 长上下文 RAG；
5. 模型吞吐测试；
6. 后续服务化部署。

优先级：高。

### 4.2 SGLang

定位：结构化生成和复杂调用流程的对比框架。

适用场景：

1. JSON 结构化输出；
2. 多轮 Agent 调用；
3. 多请求并发；
4. 复杂 Prompt 程序；
5. 与 vLLM 做性能对比。

优先级：中。

### 4.3 llama.cpp

定位：轻量量化模型推理框架。

适用场景：

1. GGUF 模型；
2. Q4/Q5/Q8 量化；
3. 低资源本地推理；
4. 边缘部署可行性测试；
5. 轻量模型测试。

优先级：中。

## 5. 候选文本模型

候选模型需要符合本地硬件条件，优先选择 30B 以内或 30B 左右可量化运行的模型。

### 第一梯队：通用文本与规则理解模型

1. Qwen3-8B  
   用途：快速 baseline、低成本部署、Prompt 调试。

2. Qwen3-14B  
   用途：第一阶段主力候选模型，兼顾效果和部署成本。

3. Qwen3-30B-A3B  
   用途：30B 级 MoE 模型可行性测试。

4. Qwen3-32B  
   用途：30B 级强基线，适合规则理解、结构化抽取和 RAG 问答测试。硬件压力较大时优先使用量化版本。

5. DeepSeek-R1-Distill-Qwen-14B / 32B  
   用途：测试推理型模型在复杂规则理解、条件判断、流程解释中的表现。

### 第二梯队：小模型与轻量部署模型

1. MiniCPM 系列  
   用途：测试小模型在业务规则问答、轻量部署和端侧推理中的表现。

2. MiniCPM-V 系列  
   用途：测试图文混合文档、截图、扫描件、表格图片理解能力。

3. 3B 级小模型  
   用途：测试小模型在 Agent、工具调用、规则问答中的能力边界。

4. Qwen3-4B / Qwen3-1.7B  
   用途：作为轻量 baseline，用于速度、成本和小模型微调实验。

### 第三梯队：国产生态模型

1. GLM 系列  
   用途：结合智谱生态，测试中文规则理解和结构化输出。

2. ERNIE / 文心相关开源模型  
   用途：测试中文文档理解、OCR 后文本理解、业务规则问答。

3. Baichuan / InternLM / Yi 等模型  
   用途：作为补充对比，观察不同国产模型在中文业务规则场景中的差异。

### 专项方向：Tabular Foundation Models

老师给出的 TabFM 可作为角色 B 的新增调研线。它不是通用聊天 LLM，而是面向结构化表格数据的基础模型，适合做分类、回归、表格规则预测和小样本表格建模实验。

候选模型与基线：

1. TabFM  
   用途：测试零样本/少样本表格分类与回归能力，验证其是否能作为 M1 抽取结果后的表格决策模型。

2. TabPFN  
   用途：作为成熟的 tabular foundation model 对照基线，和 XGBoost / LightGBM / TabFM 做效果、速度和样本效率比较。

3. XGBoost / LightGBM  
   用途：传统强基线，用于判断 foundation model 在业务表格任务上是否真正有优势。

与 M1/M2 的关系：

1. M1：LLM/OCR 从业务文档抽取规则字段、条件、阈值和产品属性，形成结构化表格；
2. TabFM/TabPFN：在抽取后的表格上做标签预测、规则适用性判断、风险等级分类或数值估计；
3. M2：RAG 负责回答规则来源和解释，Tabular model 负责对结构化表格做可量化预测；
4. 研究重点：比较“LLM 直接判断”和“LLM 抽取 + 表格模型判断”的准确率、稳定性和可解释性。

### 模型池收敛与服务运行策略

模型池按任务线组织，而不是持续扩充同一家族的通用文本模型：

| 任务线 | 首批模型 | 主要比较问题 |
| --- | --- | --- |
| M1/M2 文本生成 | Qwen3-4B、Qwen3-8B、Qwen3-14B、现有 Qwen3.6-35B-A3B | 模型规模对结构化抽取、拒答、延迟和资源占用的影响 |
| M2 检索与排序 | Qwen3-Embedding-0.6B、BGE-M3、bge-reranker-v2-m3 | 检索召回、来源命中率和重排序收益 |
| M1 OCR/多模态文档解析 | PaddleOCR-VL-1.6、MiniCPM-V 4.6 | 扫描件、表格、版式和文档问答质量 |
| M1 抽取后的表格决策 | TabFM、TabPFN、XGBoost、LightGBM | LLM 直接判断与结构化后预测的差异 |

Qwen3 的 4B、8B、14B 和 35B 已足以构成同家族、不同规模的控制组。
除非出现明确的能力缺口，不再优先下载更多 Qwen 通用文本模型；后续优先补齐
Embedding/Rerank、OCR/VLM 和表格模型的能力空白。

开发机采用“一次只常驻一个待测生成模型”的策略：

1. 4B 作为快速开发和接口连通模型，可按需保留；
2. 8B、14B、35B 逐个启动、逐个完成评测后停止；
3. 35B 仅作为质量上限对照，不作为日常常驻服务；
4. Embedding、Rerank、OCR/VLM 进行离线或单服务测试时，应先停止不参与当前实验的生成模型；
5. TabFM/TabPFN 使用独立 Python 3.11 环境，不安装到 `wzh_vllm`，也不作为 OpenAI-compatible 聊天服务运行。

截至 2026-07-10，35B 服务已从端口 8001 停止；其 GGUF 文件保留，后续需要
质量上限对照时再重新启动。

## 6. 文档解析与 OCR 模型

业务规则文档可能包含 PDF、扫描件、图片、表格、印章、公式、复杂排版，因此需要单独调研 OCR 与文档解析模型。

候选方向：

1. PaddleOCR / PP-OCR；
2. PaddleOCR-VL / PaddleOCR-VL-1.6；
3. GLM-OCR；
4. MiniCPM-V / MiniCPM-V 4.6；
5. Qwen-VL / Qwen3-VL。

第一阶段优先级：

1. 可编辑文本类文档：直接解析文本；
2. PDF 文档：先尝试文本抽取，再补 OCR；
3. 扫描件/图片：使用 OCR 或多模态模型；
4. 表格类文档：结合 Excel 解析和 OCR 表格识别；
5. 复杂版式文档：纳入后续专项测试。

## 7. Embedding 与 Rerank 模型

候选方向：

1. BGE-M3；
2. bge-reranker 系列；
3. Qwen Embedding 系列；
4. Jina Embeddings / Jina Reranker。

实验指标：

1. Top-K 命中率；
2. 来源命中率；
3. Rerank 后正确片段排序；
4. 问答可追溯率；
5. 响应延迟。

## 9. Benchmark 指标

每个模型需要记录：

1. 模型名称；
2. 推理框架；
3. 量化方式；
4. 显存占用；
5. 首 token 延迟；
6. 平均生成速度；
7. 并发 1/2/4/8 响应情况；
8. 最大上下文长度；
9. JSON 输出稳定性；
10. 规则抽取准确率；
11. RAG 问答质量；
12. 部署稳定性。

## 10. 可沉淀研究问题

角色 B 的模型侧工作可以围绕以下问题持续记录实验：

1. 小模型在 M1 结构化规则抽取中的 JSON 稳定性、字段完整性和人工修正成本；
2. OCR/文档解析模型质量对 M1 抽取和 M2 RAG 来源命中的影响；
3. Embedding / Rerank 模型对业务规则问答来源命中率和答案一致性的提升；
4. LLM 直接判断 vs LLM 抽取后交给 TabFM/TabPFN 判断的效果差异；
5. 不同推理框架、量化精度和上下文长度下的速度、显存和效果折中；
6. 面向本项目业务文档的轻量微调、LoRA/QLoRA 或 Prompt tuning 是否值得投入。
