# 03 技术架构与模块设计

## 1. 总体架构

平台建议采用以下结构：

```text
前端页面
  ↓
API 服务层
  ↓
LLM 业务逻辑层
  ↓
RAG 知识库层
  ↓
Pydantic 规则结构层
  ↓
本地模型服务层
  ↓
评测 Harness 与日志观测层
```

## 2. 前端页面层

前端页面主要包括：

1. 首页 Dashboard；
2. 文档管理；
3. M1 规则解析；
4. M2 规则问答；
5. 规则抽取结果展示；
6. 人工审核；
7. 模型选择；
8. 模型评测；
9. 实验结果展示。

第一阶段重点是让流程清楚，不追求复杂交互。

2026-07-27 本机工作区开始起草一个 `/m1` 页面，用于展示“原文定位 -> 规则候选 ->
Pydantic 校验 -> 人工复核 -> M2 载荷”的最小链路。该页面当前尚未完成静态交互与测试，
只使用确定性文本规则基线；不得将它表述为 GB10 OCR/VLM、模型抽取或真实入库结果。

## 3. API 服务层

API 层建议使用 FastAPI。

核心接口包括：

1. `GET /api/health`：健康检查；
2. `GET /api/models/list`：模型列表；
3. `POST /api/models/test`：模型连通性测试；
4. `POST /api/documents/upload`：文档上传；
5. `POST /api/documents/ingest`：文档解析、切分、入库；
6. `POST /api/rag/query`：RAG 问答；
7. `POST /api/rules/extract`：规则抽取；
8. `POST /api/rules/review`：人工审核结果提交；
9. `POST /api/evaluation/run`：批量评测；
10. `GET /api/evaluation/results`：评测结果查询。

LangServe 可作为后续标准化封装方案，在核心链路稳定后再引入。

本机 M1 页面草稿计划使用独立的 `/api/m1/sample`、`/api/m1/extract` 和
`/api/m1/review` 演示接口。它们在完成测试、持久化设计与 GB10 模型接入前不替代既有
`/api/rules/*` 正式接口，也不写入知识库。

## 4. LLM 业务逻辑层

LLM 业务逻辑层负责：

1. 场景识别；
2. 用户意图识别；
3. Prompt 上下文构建；
4. 文档解析调度；
5. 规则抽取；
6. RAG 检索问答；
7. 结构化输出；
8. 人工审核流转；
9. Agent 流程编排；
10. 结果评估。

第一阶段建议采用 LangChain + LangGraph 的轻量流程编排。不要过度构建复杂自治 Agent。

## 5. RAG 知识库层

RAG 知识库层负责：

1. 文档切分；
2. 元数据管理；
3. 向量入库；
4. BM25 检索；
5. Hybrid 检索；
6. Rerank；
7. 来源追溯；
8. 多版本规则管理。

第一阶段可先支持：

1. 普通切分；
2. Markdown 结构切分；
3. 向量检索；
4. 来源返回。

后续补充：

1. Hybrid 检索；
2. Rerank；
3. 父子分段；
4. 上下文压缩；
5. 长上下文对比实验。

## 6. Pydantic 规则结构层

Pydantic 用于描述关键规则和统一数据格式。

建议设计：

### RuleSource

描述规则来源：

- document_id；
- document_name；
- chunk_id；
- page_no；
- section_title；
- quote；
- version。

### BusinessRule

描述通用业务规则：

- rule_id；
- rule_name；
- scenario；
- condition；
- action；
- constraints；
- source；
- confidence；
- status。

### UDFFieldRule

描述统一数据格式字段：

- field_name；
- field_type；
- required；
- aliases；
- validation_rule；
- example；
- source。

### DocumentExtractResult

描述文档抽取结果：

- document_id；
- rules；
- fields；
- warnings；
- confidence；
- validation_errors；
- need_human_review。

### RuleReviewResult

描述人工审核结果：

- rule_id；
- reviewer；
- status；
- comments；
- corrected_rule；
- reviewed_at。

### EvalResult

描述评估结果：

- task_id；
- model_name；
- score；
- latency_ms；
- source_hit；
- json_valid；
- pydantic_valid；
- risk_level；
- reasons。

## 7. Agent 流程设计

第一阶段使用轻量状态机。

建议节点：

1. Router Node：判断 M1/M2；
2. Document Parser Node：解析文档；
3. Rule Extraction Node：抽取规则；
4. RAG Retrieval Node：检索知识库；
5. Rule QA Node：生成角色化问答；
6. Pydantic Validation Node：校验结构化结果；
7. Human Review Node：生成人工审核记录；
8. Evaluation Node：评估结果；
9. Trace Node：记录日志和来源。

建议状态结构：

```json
{
  "task_id": "",
  "scenario": "m1_rule_extraction",
  "user_input": "",
  "document_ids": [],
  "role": "",
  "retrieved_docs": [],
  "extracted_rules": [],
  "validated_result": {},
  "answer": "",
  "eval_result": {},
  "trace_id": ""
}
```

## 8. 日志与观测

第一阶段先做本地日志和评测结果记录。

需要记录：

1. 用户请求；
2. 场景；
3. 模型名称；
4. Prompt 摘要；
5. 检索结果；
6. 输出结果；
7. 来源信息；
8. 结构化校验结果；
9. 评估指标；
10. 错误信息；
11. 耗时。

Langfuse 可以作为后续接入方向，用于 LLM trace、prompt 管理、评分和成本统计。

## 9. OpenCode 与 MCP 适配层

OpenCode 作为可替换的 Agent 编排入口，不替代现有 Web、FastAPI 或 RAG 数据层。新增 MCP Adapter 时应遵循以下约束：

1. MCP 工具通过 `RAGService` 或稳定业务 API 访问数据，不直接绕过业务层操作数据库；
2. MCP 返回现有 `document_id`、`chunk_id`、来源、分数和集合名称；
3. 首版提供 `knowledge_search`、`knowledge_get_source`、`knowledge_list_collections` 三个只读工具；
4. M1 的 OCR、规则抽取和评测工具在只读闭环稳定后加入，并默认要求确认；
5. OpenCode 中的不同逻辑 Agent 可绑定不同模型，但 GB10 运行时遵守一次尽量只常驻一个生成模型；
6. 不在主线部署第二套 ChromaDB、Elasticsearch 或文档管理页面。

该适配层应保持足够薄，使未来替换 OpenCode、MCP SDK 或模型服务时，不影响 `RAGService` 和现有页面。
