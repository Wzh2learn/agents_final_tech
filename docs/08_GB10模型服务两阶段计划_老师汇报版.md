# 基于 GB10 的 M1/M2 本地模型服务两阶段计划

## 一、项目背景与目标

现有 AI Model 系统主要通过外部 API 调用大模型。本项目计划利用实验室 NVIDIA GB10 开发机，探索适合业务任务的开源模型，在保证效果可验证的前提下形成可独立部署的本地模型服务。

模型工作聚焦两个任务：

- **M1：业务规则文档结构化抽取。** 从文本、PDF、扫描件和表格中抽取字段、条件、阈值、动作及来源，输出可校验的统一 JSON。
- **M2：业务规则知识库问答。** 基于业务文档完成检索、重排序、答案生成、来源引用和无依据拒答。

项目不直接改造企业现有 AI Model/Agent 系统，而是通过 OpenAI-compatible API 保持松耦合。上层系统只依赖统一的请求、响应和模型名称，不依赖 GB10 上的模型权重、推理框架和运行环境。这样可以独立替换模型、调整量化方式或进行轻量微调，不影响已有系统主体。

## 二、现有基础

GB10 开发机具有 121 GiB 统一内存，目前已完成以下准备：

1. Qwen3-4B、8B、14B 和 Qwen3.6-35B-A3B 的 GGUF 模型部署及 OpenAI-compatible API 连通；
2. 四个脱敏 M1/M2 样例的 JSON、引用和拒答格式测试全部通过；
3. Qwen3-Embedding-0.6B、BGE-M3 和 bge-reranker-v2-m3 完成离线冒烟测试；
4. PaddleOCR-VL、MiniCPM-V、Qwen3-VL 等文档多模态模型已下载，待建立正式 OCR 测试集；
5. TabFM 和 TabPFN 已建立独立实验环境并完成基础推理验证。

上述结果说明本地部署链路可行，但当前样例只验证服务和输出格式，尚不能代表正式业务数据上的模型质量。下一步工作的核心是建立数据集、形成数字结果并收敛模型方案。

## 三、总体技术方案

```text
现有页面 / Agent 系统
        ↓ 统一任务协议
模型适配层（模型选择、Prompt、JSON Schema）
        ↓ OpenAI-compatible API
GB10 本地模型服务
        ├─ M1：文本模型 + OCR/VLM + 结构化校验
        └─ M2：Embedding + Rerank + 生成模型
```

模型资源按三档使用：4B/8B 用于快速开发和轻量服务，14B Q4 作为主要质量与成本候选，35B MoE Q4 作为效果上限对照。为保证资源稳定，一次只常驻一个待测生成模型；OCR、Embedding、Rerank 和表格模型按实验任务单独运行。

外部 API 模型与 GB10 本地模型使用同一测试集和同一指标评测。最终不仅比较模型质量，还比较延迟、资源占用、数据可控性和部署成本。

## 四、第一阶段：数据集、模型调优与量化评测

计划周期为 4 周，目标是获得一个针对 M1/M2 有明确数字效果的本地模型方案。

### 1. 数据集建设

从脱敏业务材料中建立 M1 标注集和 M2 问答集。第一版建议分别不少于 100 条有效样例，覆盖正常、边界、冲突和无答案情况。固定训练集、验证集和测试集，测试集不参与 Prompt、检索参数或微调参数调整。

### 2. 模型基线与调优

在相同数据上比较外部 API、Qwen3-4B/8B/14B 和 35B。M1 依次评估 Prompt、JSON Schema、校验重试、OCR/VLM 和 LoRA/QLoRA；M2 依次评估文档切分、Embedding、Top-K、Rerank、上下文构建和拒答策略。每次只改变一个主要变量，保留配置、原始输出和失败样例。

轻量微调不是默认动作。只有 Prompt、结构化约束和 RAG 基线稳定后，且训练数据量与质量足够时，才对 8B/14B 开展 LoRA/QLoRA，并以独立测试集判断是否值得保留。

### 3. 核心指标

| 任务 | 评价内容 | 建议阶段目标 |
| --- | --- | --- |
| M1 | JSON 合法率、Pydantic 通过率、字段 Precision/Recall/F1、人工修正率 | JSON 合法率 ≥98%，Pydantic 通过率 ≥95%，字段 F1 相对基线提升 ≥5 个百分点 |
| M2 检索 | Recall@5、来源命中率、Rerank 前后增益 | Recall@5 ≥90%，明确报告 Rerank 增益 |
| M2 回答 | 答案准确率、来源一致性、无依据拒答率、人工评分 | 来源命中率 ≥85%，无依据拒答率 ≥90%，综合质量相对基线提升 ≥5 个百分点 |
| 部署 | 首 Token 延迟、生成速度、总耗时、峰值内存、稳定性 | 完成重复测量，候选模型可连续完成整套测试且服务无崩溃 |

指标阈值可在首次标注一致性检查后调整一次，但不能根据最终测试结果倒推验收标准。

### 4. 第一阶段交付物

- M1/M2 脱敏数据集、标注规范和数据划分；
- 可重复运行的评测脚本和原始结果；
- 外部 API、本地基线和调优方案对比表；
- GB10 上效果、速度和资源占用的 Pareto 分析；
- 一个主力模型服务、一个轻量备选服务及统一 API；
- 模型选择报告、失败样例和已知限制。

## 五、第二阶段：界面展示、服务固化与交接

计划周期为 2 周。该阶段不重新开发完整平台，而是复用已有系统代码完成最小效果展示。

界面包含三个部分：M1 页面展示文档抽取结果、来源和校验状态；M2 页面展示问题、答案、引用片段和拒答结果；模型实验页面展示基线与调优后的指标、延迟、资源占用及典型样例。

模型侧同时冻结推荐模型、推理参数、Prompt/Schema、数据版本和 API 协议，提供健康检查、启动停止、模型切换、错误处理、调用示例和验收用例。完成标准是：已有页面能够调用 GB10 服务展示 M1/M2 效果，接手同学无需理解模型权重和环境细节即可继续开发。

第二阶段交付物包括：可演示页面、稳定模型 API、部署与调用文档、联调样例、验收结果和工程交接清单。

## 六、人员分工

### 角色 B：模型与数据负责人

负责 GB10 环境和资源管理、模型部署、M1/M2 数据集、模型基线、Prompt 与结构化约束、检索与重排、可选 LoRA/QLoRA、性能测试、模型 API、数字结果和最小界面验证。核心责任是证明模型在指定任务上“有效、可量化、可复现、可服务化”。

### 协作同学：Agent 与工程集成负责人

在模型方案冻结后，负责 M1/M2 Agent 流程调优、业务 Prompt 深化、工具调用、状态管理、现有系统适配、前后端联调、企业接口接入、异常降级、权限和后续运维。核心责任是将模型能力转化为企业可使用的完整业务流程。

双方共同确认输入输出 Schema、数据口径、验收指标和 API 版本，并共同完成最终 Demo 和交接验收。模型研究与企业工程通过版本化接口协作，避免互相阻塞。

## 七、可延伸研究方向

在完成 M1/M2 主线后，可进一步形成以下研究问题：

1. 小模型在业务规则结构化抽取中的可靠性、错误类型和人工修正成本；
2. OCR/版式解析误差对 M1 抽取和 M2 RAG 来源命中的传递影响；
3. Embedding 与 Rerank 对规则问答可追溯性的实际增益；
4. “LLM 直接判断”与“LLM 抽取 + TabFM/TabPFN/XGBoost 判断”的效果差异；
5. GB10 上模型规模、量化精度、推理速度和任务效果之间的 Pareto 最优方案。

这些研究方向以项目真实实验数据为基础，可用于后续小论文、研究生开题和本地模型部署实践总结，但不影响当前两阶段交付主线。

## 八、OpenCode 多智能体接入方案

在老师提出 OpenCode 路线后，项目采用“OpenCode + 现有 RAG MCP + GB10 本地模型服务”的松耦合方案。

现有系统已经具备文档管理、PGVector、BM25/混合检索、来源追溯和展示页面，因此不重新建设独立的 ChromaDB 或 RAGFlow 知识库。项目只增加一层薄 MCP Adapter，把现有知识能力以标准工具提供给 OpenCode。这样既能验证多智能体协作，也能保留已有系统的数据、接口和页面成果。

第一步先提供知识检索、来源读取和知识库列表三个只读工具，完成 M2 检索、引用和拒答闭环；第二步接入 OCR/VLM、规则抽取和 Pydantic 校验，完成 M1 闭环；最后再拆分主协调 Agent、M1 Agent、M2 Agent 和校验 Agent。

模型分工采用“逻辑多 Agent、物理模型按需运行”：Qwen3-14B 作为日常主模型，PaddleOCR-VL/Qwen3-VL 负责文档解析，Embedding/Reranker 负责确定性检索，35B MoE 仅处理困难样例和质量上限对照。该方式符合 GB10 的资源特点，也避免同时常驻多个大模型造成浪费。

该路线的核心优势是：OpenCode、现有业务系统和模型服务彼此可替换；模型实验不影响业务数据；Agent 工程可以在模型能力冻结后由协作同学继续完成。
