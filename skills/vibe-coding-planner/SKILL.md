# Vibe Coding 计划拆解器

## 用途

当你用一句话描述"我想做个 XXX 系统/页面/功能"时，这个技能会帮你把模糊的"vibe"拆解成：
- 明确的需求定义
- 系统/模块划分
- 开发里程碑（按天/迭代）
- 风险点和前置验证任务

这是 Vibe Coding 从"感觉"到"计划"的桥梁。

## 如何触发

你可以这样对我说：

```
/plan 我想做一个用户管理系统
```

或者：

```
帮我用 Vibe Coding 的方式规划一下这个功能：
[描述你的想法]
```

## 工作流程

### 第一步：5W1H 追问

我会通过以下问题帮你明确需求：

1. **What（是什么）**：核心功能是什么？
2. **Why（为什么）**：要解决什么问题？用户价值是什么？
3. **Who（谁用）**：目标用户是谁？有哪些角色？
4. **When（何时）**：期望的交付时间？有无里程碑要求？
5. **Where（哪里）**：部署环境？技术栈限制？
6. **How（怎么做）**：有无特定的技术偏好或约束？

### 第二步：模块拆解

基于你的回答，我会将系统拆解为：

- **核心模块**：必须实现的功能模块
- **辅助模块**：支撑性功能（如日志、监控）
- **可选模块**：增强型功能（可后续迭代）

### 第三步：里程碑规划

输出格式如下：

| 里程碑 | 目标 | 关键任务 | 预计时间 | 验收标准 |
|--------|------|----------|----------|----------|
| M1 | 基础架构搭建 | 项目初始化、数据库设计 | 1-2天 | 能运行 Hello World |
| M2 | 核心功能实现 | 用户注册、登录 | 3-5天 | 用户可以注册登录 |
| M3 | 功能完善 | 权限管理、日志 | 2-3天 | 完整的用户管理流程 |
| M4 | 测试和优化 | 单元测试、性能优化 | 2-3天 | 测试覆盖率 > 80% |

### 第四步：风险清单

识别潜在风险：

- **技术风险**：技术栈不熟悉、第三方依赖不稳定
- **需求风险**：需求不明确、频繁变更
- **资源风险**：时间不足、人力不够
- **集成风险**：与现有系统集成困难

每个风险都会给出缓解措施。

## 完整示例

### 用户输入

```
/plan 我想做一个博客系统，支持 Markdown 写作和评论功能
```

### 输出计划

#### 1. 需求明确

**核心功能**：
- 用户可以用 Markdown 写博客文章
- 支持文章的发布、编辑、删除
- 读者可以对文章进行评论
- 支持文章分类和标签

**用户角色**：
- 作者：可以写文章、管理自己的文章
- 读者：可以浏览文章、发表评论
- 管理员：可以管理所有文章和评论

**技术约束**：
- 后端：Python + FastAPI
- 前端：React
- 数据库：PostgreSQL
- Markdown 渲染：前端使用 marked.js

#### 2. 模块划分

**核心模块**：
1. 用户认证模块（注册、登录、权限）
2. 文章管理模块（CRUD、Markdown 解析）
3. 评论模块（发表、回复、删除）
4. 分类标签模块（分类管理、标签管理）

**辅助模块**：
5. 文件上传模块（图片上传）
6. 搜索模块（全文搜索）

**可选模块**：
7. 点赞收藏模块
8. RSS 订阅模块

#### 3. 开发里程碑

| 里程碑 | 目标 | 关键任务 | 预计时间 | 验收标准 |
|--------|------|----------|----------|----------|
| M1 | 项目初始化 | 搭建前后端框架、数据库设计 | 1天 | 项目可运行，数据库表创建完成 |
| M2 | 用户认证 | 实现注册、登录、JWT 认证 | 2天 | 用户可以注册登录，获取 token |
| M3 | 文章管理 | 实现文章 CRUD、Markdown 渲染 | 3天 | 作者可以写文章并预览 |
| M4 | 评论功能 | 实现评论发表、回复、删除 | 2天 | 读者可以评论文章 |
| M5 | 分类标签 | 实现分类和标签管理 | 1天 | 文章可以分类和打标签 |
| M6 | 测试优化 | 单元测试、性能优化、安全加固 | 2天 | 测试覆盖率 > 80%，无明显性能问题 |

**总计：约 11 天**

#### 4. 风险清单

| 风险类型 | 具体风险 | 影响 | 缓解措施 |
|----------|----------|------|----------|
| 技术风险 | Markdown XSS 攻击 | 高 | 使用 DOMPurify 清理 HTML |
| 技术风险 | 图片上传安全问题 | 中 | 文件类型验证、大小限制 |
| 需求风险 | 评论功能需求不明确 | 中 | 先实现简单评论，后续迭代 |
| 资源风险 | 11 天时间可能不够 | 中 | 优先实现核心功能，可选模块后续迭代 |

#### 5. 前置验证任务

在正式开发前，建议先验证：

1. **技术选型验证**：
   - 搭建 FastAPI + React 的最小可运行项目
   - 验证 Markdown 渲染效果

2. **数据库设计验证**：
   - 设计数据库 ER 图
   - 评审表结构是否合理

3. **安全性验证**：
   - 研究 Markdown XSS 防护方案
   - 设计文件上传安全策略

## 遵循的原则

本技能严格遵循 Vibe Coding 的核心原则：

1. **意图先于实现**：先明确"要什么"，再考虑"怎么做"
2. **分层设计**：从系统到模块逐层细化
3. **上下文管理**：记录关键决策和约束条件
4. **质量前移**：在计划阶段就考虑测试和安全
5. **迭代优化**：按里程碑逐步推进，而不是一次性完成

## 注意事项

- 计划不是一成不变的，可以根据实际情况调整
- 优先实现核心功能，可选功能可以后续迭代
- 每个里程碑完成后都要进行验收，确保质量
- 风险要提前识别和缓解，不要等到出问题再处理
