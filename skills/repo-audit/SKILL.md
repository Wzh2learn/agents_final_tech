# Repo Audit — 仓库治理审计循环

> 设计哲学：文档/代码/规则/git 记录会以远超"下次想起来查一下"的速度腐化。审计不是"读一遍找
> 错字"，是对抗性验证——默认一切"已完成"的声明是假的，直到给出 diff/实测/字节级证据。修复
> 动作本身同样要被审计，因为它是刚生产出来、还没被验证过的新内容。
> ⚠️ 弹性声明：下面的步骤/清单是本域实证出来的起点，遇到新的腐化模式随时增补，不要死守清单。

## 核心原则

1. **永不信任"已修复"的声明**——commit message、"他说改完了"、"应该没问题了"都只是需要验证
   的假设，不是结论。只信：重新读 diff、重新跑测试/脚本、字节级核对文件内容。
2. **修复动作本身是审计对象**——刚落地的 fix commit 和刚生成的报告，跟它们要修复的旧内容一样
   可能有问题（本域实证：修复 commit 自己造出新的重复编号/算术错/漏索引；自检 commit 的
   message 说做了替换但 diff 只换了标签）。
3. **同一模式复发 ≥2 次，别再指望"下次记得"**——写进 memory/协议只是留档，真正止血是把可机械
   判定的部分变成 commit 路径上的 hook（本域实证：README 索引打地鼠、CJK 字节复核，从"人工
   纪律"升级成 pre-commit 拦截后才真正不再复发）。
4. **报告只列可核查的具体证据**——每条发现必须有文件名+行号+原文引用，没有就别写；核实后没
   问题就明确说"已核实，无发现"，不为了显得有产出而凑数。

## 工作流

### 第 1 步：建立 ground truth

审计不是凭直觉找茬，是拿"已确认的当前事实"去对比"文档/代码实际怎么写"。开工前先从这几处
提炼本轮要用的 ground truth 清单：
- 项目的铁律记忆文件（如 `project-memory.md`）、进度权威文件（如 `HANDOFF.md`）、规则本体
  （如 `docs/协作协议.md`）
- 若涉及具体数值/时刻/配置（比如某个调度时刻、某个开关的当前默认值），**用 `git log -S` 或
  `git blame` 核实其真实生效版本和引入的 commit**，不要凭记忆或凭上一轮审计给的 briefing——
  本域实证：审计者自己给子 agent 的 ground truth briefing 曾经把某时刻错标成"最早值"，漏了
  更早的一段沿革，被子 agent 读文档的结果反过来倒查出来。**给别人的 briefing 本身也要素审。**

### 第 2 步：定位未覆盖面

- 用户给了明确范围时，直接进入第 3 步。
- 开放式的"还有什么要审计的"/"扩大视角看看"，先枚举：哪些文件/commit 从未被本轮之前的审计
  触碰过？用 `git log --oneline -- <file>` 查某文件上次被审计相关 commit touch 的时间，或者
  直接列出文档目录全量后逐个对照"读过/没读过"清单。
- 定期主动换维度，不要一直停在同一个抽象层级：**文档时效性 → 代码正确性 → git 仓库卫生 →
  规则文档自身健康度 → 审计过程本身的收益趋势**，是本域验证过有效的几个不同"视角"，各自能
  挖出不同性质的问题——后两个"元层级"角度容易被忽略，但抓到的问题级别往往更高（规则文档自
  己内部自相矛盾、git 默认分支指针指错，都是在"扩大视角"这一步才被发现的）。
- **不要只等"他改完了"的通知才启动**：定期（比如每隔几轮实验收尾，或规则文档新增一条纪律
  之后）主动抽查最近若干个 commit 是否真的做到了已有的、尚未工具化的纪律（比如"变更是否同
  commit 同步了锚点文档"），而不是等下一次全量审计才发现连续几个 commit 都没做到——这本身
  就是第 6 步"模式升级判断"的输入来源之一：如果抽查发现某条纪律持续被漏，说明它比表面看起
  来更该优先自动化。

### 第 3 步：并行子 agent 扫描

单个问题（1-3 处需要确认的具体点）直接自己查；涉及多个文件/多个独立维度时用 Agent 工具并行
派发，每个子 agent 的 prompt 必须自包含（子 agent 看不到当前对话），且固定包含以下三段：

**a) 工具容错声明**（当前环境存在路径受限的专用工具时必加）：
> "标准 Read/Bash/Grep 工具在此环境可能无法访问该路径。请优先尝试标准工具，失败或返回异常
> 空结果时改用备选工具集。如果都完全无法访问，明确报告'工具不可达'，不要报告'文件为空'或
> '未发现问题'——这个区分很重要，过去审计中曾有工具访问错误被误判为'内容正常'的教训。"

**b) 已搁置话题规避清单**：把当前项目里"用户已明确要求不要再提"的话题列给子 agent，防止扩大
搜索时意外重新踩中已经拍板暂不处理的事。

**c) "已核实无发现"是合法输出**：明确告诉子 agent"如果查完确实没问题，直接说已核实无发现，
不要为了有产出而凑问题"，否则子 agent 倾向于为了完成任务硬造轻微发现。

子 agent 返回基础设施错误（如网关 502）时直接重试（通常是临时的），重试 2-3 次仍失败再考虑
改用自己直接查，不要无限重试同一个失败任务。

### 第 4 步：按严重度分级汇总

统一用 🔴P0（操作性风险：文档指导会导致真实数据丢失/服务中断/训练启动失败）/ 🟡P1（实质性
错误但当前未触发事故）/ ⚪P2（措辞/索引/轻微不一致）三档，同时标注：
- 这条发现是不是**已知模式的新实例**（打地鼠漏兄弟文件、message 与 diff 不符、CJK 编码损
  坏、SSOT 方向矛盾、同一句话/同一行第二处遗漏等）——是的话直接点名"第 N 次实例"，累计到位
  就在第 6 步提出升级为 hook。
- 这条发现有没有独立交叉验证过，还是只有单一信源——单一信源的发现要在报告里说清楚置信度，
  不要和已交叉验证的发现混在一起同等呈现。

### 第 5 步：验证 fix commit（任何"他改完了"通知之后的强制步骤）

1. 找到实际的 fix commit，**读完整 diff，不要只读 message**。
2. 逐条对照声称修复的每一点：diff 里真的有对应的 hunk 吗？内容是不是真的解决了问题（而不
   是只换了个标签/只改了半句话）？
3. 对 fix commit 本身应用已知模式清单做反查——它有没有在修 A 的同时在别处造出 B（同类文件
   漏改/同一句话另一处没改/新增数字没核对）？
4. 只有跑得动的才叫验证：涉及测试/脚本的声称，**实际重新跑一次拿真实退出码**，不接受"应该
   过了"。
5. 涉及并发/锁一类的代码正确性问题，不要停在"读起来逻辑对"，去追一层调用者有没有正确遵守
   约定（比如某个 skip-lock 模式要求调用者自己持锁，就去确认所有调用点是不是真的都配对包
   装了，而不是只看被检查的那一处）。

### 第 5b 步：结构重组后的路径断裂全域扫描（git mv 批次后的强制步骤）

当一次重构涉及文件移动（`git mv`）——尤其是脚本/文档从一个目录重新分组到子目录——除了重构
commit 自己声称的"N 处引用同步，残留 0"之外，还需要独立验证：

1. **建立"旧路径→新路径"映射清单**：从重构 commit 的 `--stat` 里提取所有 rename 行。
2. **全域 grep 每个旧路径**（排除 .git/ 和 archived/——后者按"archived 不回改"纪律豁免）：
   - 全路径引用（如 `scripts/env_gpu-cluster.sh`）
   - 裸文件名引用（如 `env_gpu-cluster.sh`）
   - markdown 链接引用（如 `[xxx](scripts/env_gpu-cluster.sh)`）
3. **区分"会被执行的引用"和"纯阅读参考"**：`source`/`bash`/`python3` 后面跟的路径断裂会
   直接导致运行时崩溃（🔴），文档正文里的路径引用只是误导读者（🟡）。
4. **扫描重构 commit 之后的新 commit**——有人在后续 commit 里可能用旧路径写了新引用（因为
   肌肉记忆还没更新）。
5. **特别检查 SSOT 镜像方向**：涉及 `config/` ↔ `.claude/` 双侧文件的重构，修复后必须
   确认 SSOT 侧（config）和镜像侧（.claude）内容一致——本域实证：某次修复只改了 config
   但没跑 sync_config.sh，或者改了 .claude 但 config 是 SSOT 导致下次 sync 会覆盖回去。
   diff 两侧确认逐字一致是这一步的硬输出。

本域实证（08-20 scripts 5 层重组）：重构 commit 声称"全域 11 处引用同步残留 0"，独立审计
用 grep 逐个旧路径扫描验证属实；但**后续修复 commit 把 config SSOT 和 .claude 镜像搞反
了**（改了 .claude 没改 config，导致 SSOT 侧落后于镜像侧），是路径重构审计中容易漏掉的
第二层风险。

### 第 6 步：模式升级判断

发现同一类问题第 2 次即在报告里提出"是否该自动化"的候选；第 3 次以上应该明确建议，而不是
继续记录成第 N 条人工纪律。可机械判定的模式（字符串匹配、正则、字节扫描类）优先做成
pre-commit/PreToolUse hook：识别 staged 内容 → 命中拦截并给出可定位的报错 → 环境异常时降
级放行不静默 fail-open。落地后必须自己写正反例测试用例验证（staged 一个故意违规的文件跑一
遍拿 exit code，staged 一个合规的文件确认放行），不能只信"写完了应该能拦"。

## 输出格式

```markdown
## 审计结论

### 🔴 P0
- <文件:行号> <原文引用> — <问题> — <是第几次同类实例/是否已交叉验证>

### 🟡 P1
...

### ⚪ P2
...

### ✅ 已核实无发现
<列出核实过、确实没问题的部分，体现审计的平衡性，不是只报 problem>
```

## 与其他 skill 的关系

- **neat-freak**：neat-freak 是单次会话收尾时的知识对齐（偏静态、偏例行），本 skill 是主动
  的、对抗性的、会自我迭代升级的治理循环（偏动态、偏挖掘）——常规收尾用 neat-freak，怀疑
  "节奏已经跑到审计前面"或被明确要求"审计"时用本 skill。
- **verify-before-done**：本 skill 第 5 步直接复用 verify-before-done 的"永不信任完成声明"
  精神，但 verify-before-done 验证的是一个具体的、当下的完成申报；本 skill 是把这个精神应用
  到*已经过去、以为已经结案*的 fix commit 上，且只是整个循环里的一步而不是全部。
- **code-pathology**：本 skill 管"文档/流程/规则是否腐化"，不管"代码逻辑本身对不对"——model.py
  等核心训练路径代码的系统性正确性审查、新模块合入后的交互面检查、SQL/DataWarehouse 查询逻辑病理，都是
  code-pathology 的职责（08-14 起它已扩展含 SQL 病理小节），扫描中发现这类代码层问题应指向它，
  不越界代劳；本 skill 只负责发现"这段代码/这个新功能完全没有测试覆盖"这种governance层面的
  0 覆盖信号。
- **experiment-autopsy**：不同领域（实验结果归因 vs 仓库治理），互不重叠。
- **skill-merger / skill-hook-trigger**：这两个是"skill 库自身"的治理工具；本 skill 审计对
  象是"仓库/文档/规则的治理状态"，扫描中如果发现 skill 库本身有问题（描述过期、触发重叠），
  转交给这两个处理，不越界代劳。

## 项目结构梳理（审计的延伸能力）

当用户反映"scripts/docs 太多不知道怎么看"时，不是直接开始移文件，而是先做诊断再出方案：

1. **全量枚举**：`find <目录> -type f | sort` 拿到完整文件清单+计数
2. **功能分类**：逐个文件按"长期活跃 vs 跑完归档 vs 一次性分析 vs 通用工具 vs 监控看门"
   分组——命名前缀/后缀、是否有对应的收官日志、是否被其他脚本 source/调用，是分类的三个信号
3. **出结构方案**：画出建议的子目录树 + 每个文件归属 + 风险点（哪些文件内部有相对路径引用
   会因移动而断裂）
4. **分两步执行**：
   - 第一步（零风险）：已收官的一次性 runner 归档，只 `git mv` 不改任何引用
   - 第二步（需协调时间窗）：新建子目录+移活跃文件+全域引用同步——**必须原子执行**（不能
     分多个 commit，中间状态会让正在跑的脚本找不到依赖），且不能在有实验在跑的时候做
5. **重组后强制审计**：套用上面第 5b 步全域路径断裂扫描，确认零残留

本域实证（08-20，191 个脚本文件）：诊断后按 pipeline/analysis/tools/monitors/runners 五层
分治，第一步归档 5 件零风险先行，第二步原子执行后全域 grep 验证零断裂；后续审计仍抓到 1 处
SSOT 方向反转残留（config 侧路径没跟上 .claude 侧修复），证明"声称零残留"仍需独立验证。

## 边界与安全

- 默认**只读、只出报告**，不擅自修改/合并/删除；只有用户在当次对话明确授权后才写入，且遵循
  本域既有纪律（显式路径提交，不用 `-A`；CJK 密集文档编辑后按字节级复核纪律核对）。
- 已被用户明确搁置/暂不处理的话题，除非用户主动重新提起，否则不要在后续轮次里重新提出，即
  使扫描时又碰到。
- 涉及密钥/凭证类内容：只标注"存在明文凭证风险"这一事实本身（如果用户尚未处理过这类发
  现），不展开分析其具体值或利用方式；如果用户已明确表示"先不管"，则完全不再提及。
