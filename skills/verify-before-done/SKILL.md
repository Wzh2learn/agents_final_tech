# Verify Before Done：完成申报前的双重验收

> 本域血泪案例（为什么这个 skill 必须触发）：
> - 1500 步观察曾报"观察线严格未触发（2 段）"，重算全序列实为 **5 段连爬**——只看尾部数据就下了全局结论（HANDOFF 07-27 修正条目）
> - baseline_v1 训练"loss 3.547→0.197、0 错误"看起来完美，实际是 uu_sim→0.99 的**退化解** + last_pos bug 双缺陷
> - 铁律呼应：`project-memory.md`"助手'全部完成'汇报需逐项核对勾选状态"；"修好一个真实 bug ≠ 解释了观察到的异常"

## 第一段：对抗式审查（假设它是坏的）

默认立场：**代码/结论是坏的，直到证明不是。** 不客气、不提修复方案、只找茬。
先读目标 spec（Goal Card / 任务描述）：「完成」到底要求什么？再逐行读 diff。

### 11 条"假完成"捷径清单（逐条过）

1. **放松测试** — 断言被削弱或删除，红变绿
2. **吞掉错误** — try/except 把失败藏起来而不是处理
3. **假改名** — 函数换个名就算"修了"，行为没变
4. **桩返回值** — 硬编码返回值骗过单个测试
5. **注释当修复** — bug 变成了 TODO
6. **只走 happy path** — 空输入/缺文件/异常分支没处理
7. **范围蔓延** — 与目标无关的"顺手改"
8. **发明 API** — 调用了源码里不存在的方法/参数
9. **静默决策** — 架构级选择（schema/采样方式）没有上报就做了
10. **mock 骗过** — 测试 mock 掉了它声称要验证的那个东西
11. **偏题完成** — 代码能跑、测试通过，但解决的不是要求的目标

**输出**（JSON，不写散文）：`{"passes": false, "failures": [{"line": 42, "shortcut": "吞掉错误", "why": "..."}]}`
真过了就一句话说明；大多数时候过不了。

## 第二段：完成门（本轮实跑验证）

```
没有本轮新鲜验证证据，禁止任何完成申报
```

宣称 "done / fixed / 通过 / 绿了" 之前的门函数：

1. **定位** — 哪条命令能证明这个声明？
2. **实跑** — 本轮完整执行它
3. **读全** — 完整输出 + 退出码 + 失败计数
4. **核对** — 输出真的支持声明吗？
5. **然后才** — 带着证据做声明

### 常见虚假声明 → 实际需要什么

| 声明 | 需要 | 不算数 |
|---|---|---|
| 测试通过 | 本轮跑测试，exit 0，0 失败 | "应该能过"、上次的运行结果 |
| bug 修好了 | 复现原症状，亲眼看它不再发生 | 改了代码、"按理说修了" |
| 训练健康 | 守卫指标（uu_sim 分布形态/pos_sim/margin），不只 loss | "loss 降得很好"（v1 教训：loss 0.197 是退化解） |
| 助手/子 agent 完成 | 亲自读 diff / log，核对声称的改动真实存在 | 对方自己的"success"汇报 |
| 数字结论 | 写明来源 log 路径 + 全序列/全分片核算 | 只看尾部/单 rank 数据外推全局 |

### 红旗词（出现即说明你正要跳过验证）

"should / probably / 应该 / 看起来没问题 / 大概率" · 跑命令前就写"Done!/完美" · 信任子 agent 的自报成功 · "就这一次" · 部分验证外推整体（linter 过了 ≠ build 过）

## 何时触发（If-Then，已注册进协作协议 §五）

- 任何"完成/修复/通过"表述前（含心里想的）
- git commit、任务勾选、交接 HANDOFF 前
- 验收 remote server agent汇报时（逐项核对，不转述其结论）
- 向 user 报实验数字前（数字必须可溯源到 log 路径）
